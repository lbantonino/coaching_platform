## 1. Le projet en 30 secondes

Une application web SaaS pour coachs sportifs (Running, Musculation, Hyrox, Hybride). Un coach crée des programmes d'entraînement sur plusieurs semaines, les publie, et ses sportifs les consultent sur téléphone puis donnent leur ressenti. Un administrateur gère la plateforme.

**« SaaS multi-tenant »** : plusieurs coachs utilisent la même application et la même base de données, mais chacun ne voit **jamais** les données des autres. Un coach (ou un studio) = une **organisation**. C'est la contrainte n°1 du projet, et elle explique beaucoup de choix ci-dessous.

**Le nom : Coory. Le positionnement** (détail dans `docs/16_POSITIONNEMENT.md`) : un concurrent, Athleex, fait du coaching généraliste orienté musculation et business. Coory ne le copie pas : même socle, mais spécialisé **Running, Hyrox et Hybride**, avec dix différences prévues (allures calculées par sportif, mode club, minuteur de séance, boîte à outils Hyrox, import de programmes existants, marque du coach, IA d'assistance validée par le coach, import Strava/Garmin, hors ligne). Phrase pour un recruteur : « On n'a pas cherché la parité avec le concurrent, on a choisi une niche qu'on connaît et des fonctions qu'il ne fait pas bien. »

## 2. La stack, et pourquoi chaque outil

| Outil | Rôle | Pourquoi lui |
|---|---|---|
| **Next.js 16** (App Router) | Le site ET le serveur, dans une seule application | Évite d'avoir un frontend et un backend séparés à maintenir. Le serveur Next exécute la logique métier. |
| **React 19** | Les composants d'interface | Standard du marché, imposé par Next. |
| **TypeScript strict** | Le langage | Les erreurs de type sont détectées avant d'exécuter le code. « Strict » = pas de raccourcis permissifs. |
| **Tailwind CSS 4** | Le style | Styles écrits directement dans les composants, rapide, cohérent, responsive facile. Les couleurs et tailles du design system y sont déclarées une seule fois (tokens). |
| **Lucide** | Les icônes | Imposées par le design system Coory : traits fins, monochromes, sans emoji. |
| **Supabase** | Base PostgreSQL + comptes (Auth) + fichiers (Storage) | Un seul service pour trois besoins. Et surtout la **RLS** de PostgreSQL (voir §5). |
| **Zod** | Valider les données reçues | Tout ce qui vient du navigateur est vérifié côté serveur avant usage. |
| **Docker** | Faire tourner Supabase sur le Mac | Développer hors ligne, gratuitement, et remettre la base à zéro en quelques secondes. Uniquement en développement. |
| **pgTAP** | Tests de la base de données | Prouver par des tests que la sécurité SQL fonctionne. Intégré à Supabase. |
| **Playwright** | Tests « comme un humain » | Un robot ouvre un vrai navigateur (ordinateur et téléphone), clique, remplit, vérifie. |
| **Vitest** | Tests unitaires | Vérifie en une fraction de seconde les règles « pures » (validations, calculs, jetons), sans base ni navigateur. |
| **ESLint + Prettier** | Qualité et format du code | Repérer les erreurs courantes, garder un style uniforme. |
| **SDK Anthropic** (`@anthropic-ai/sdk`) | L'Assistant IA (Claude), depuis le 13/11 | Le client officiel de l'API Claude, appelé uniquement par une action serveur : la clé ne quitte jamais le serveur. Réservé à l'abonnement Coory, limité par la base (D-168). |

**Ce qu'on a volontairement refusé** (et pourquoi) : un backend séparé (Express, NestJS), un ORM (Prisma, Drizzle), GraphQL, Redis. Chacun ajoute de la complexité sans besoin réel aujourd'hui : Next + Supabase couvrent tout. La règle du projet : **on n'ajoute un outil qu'au moment où une fonctionnalité le justifie**. Exemple : Zod est arrivé avec le premier formulaire, Playwright avec le premier parcours utilisateur, pas avant.

**Phrase pour un recruteur** : « Un monolithe Next.js en TypeScript, Supabase pour la base, l'auth et la sécurité au niveau des lignes, et des tests à trois niveaux : SQL, HTTP et navigateur. Pas d'outil ajouté sans besoin démontré. »

Les crochets comme `[orgId]` sont des **segments dynamiques** : `/coach/o/1234/sportifs` donne `orgId = "1234"`. Les parenthèses comme `(auth)` sont des **groupes de routes** Next : ils rangent les fichiers sans apparaître dans l'URL. `src/app/(coach)/coach/page.tsx` répond à `/coach`.

**Pourquoi séparer `app/` et `features/` ?** `app/` contient seulement l'affichage. La logique (« qui a le droit ? », « que valider ? ») est dans `features/`. Ainsi la même règle sert à plusieurs pages, et on la teste une seule fois.

## 4. Comment l'interface parle au serveur

Next.js offre trois mécanismes, chacun pour un usage précis :

- **Server Component** (lire) : la page est calculée sur le serveur, qui lit la base et envoie du HTML. Exemple : `/coach` affiche ton organisation.
- **Server Action** (modifier) : un formulaire appelle directement une fonction serveur. Exemple : `login()` dans `features/auth/actions.ts`. Important : une action est appelable par n'importe qui sur Internet, donc **elle revérifie toujours** identité, droits et données.
- **Route Handler** (vraie adresse HTTP) : pour ce qui n'est pas une page. Exemple : `/auth/confirm`, qui reçoit le lien du mail de réinitialisation.

## 5. La sécurité en trois couches (le cœur du projet)

Une requête traverse trois barrières successives. Si l'une a un bug, la suivante protège encore.

1. **Le proxy** (`src/proxy.ts`) : avant chaque page, il rafraîchit la session et renvoie vers `/login` si on n'est pas connecté. C'est du confort, pas la vraie protection.
2. **Les garde-fous serveur** (`src/features/auth/guards.ts`) : `requireCoach()`, `requireAthlete()`, `requirePlatformAdmin()`, `requireOrgAccess(id)`. Appelés en tête de chaque page ou action protégée. Ils vérifient le **rôle réel** dans la base.
3. **La RLS PostgreSQL** (Row Level Security, dans `supabase/migrations/`) : la base elle-même filtre chaque ligne. Même si le code oubliait une vérification, un coach ne recevrait jamais une ligne d'une autre organisation.

Règles qui en découlent :
- Le navigateur n'envoie **jamais** « je suis de l'organisation X » : le serveur le déduit de la session.
- Un rôle ne se lit **jamais** dans des données modifiables par l'utilisateur.
- « Interdit » et « n'existe pas » donnent la même réponse : on ne révèle pas l'existence d'une donnée.
- Les pages personnelles ne sont jamais mises en cache (`Cache-Control: private, no-store`).
- La **clé secrète** Supabase (qui contourne la RLS) n'est utilisée que dans un fichier serveur isolé (`lib/supabase/admin.ts`), pour une seule procédure : créer le compte d'un sportif qui accepte une invitation valide. On a vérifié qu'elle n'apparaît dans aucun fichier envoyé au navigateur.
- Dans un fichier `"use server"`, **chaque fonction exportée est une porte d'entrée publique**. On n'y exporte que les actions voulues, les autres restent internes.
- Quand une écriture touche plusieurs tables ou ne doit jamais être faite « à la main » (publier une version figée d'un programme), elle passe par une **fonction SQL contrôlée** : le navigateur n'a aucun droit d'écriture direct sur ces tables, la fonction revérifie l'appartenance à l'organisation, et tout se fait dans une seule transaction.

**Phrase pour un recruteur** : « Défense en profondeur : redirection optimiste au proxy, autorisation explicite dans chaque action serveur, et isolation finale par RLS PostgreSQL, testée automatiquement avec deux organisations. »

## 6. La méthode de travail

- **Lire avant d'écrire.** Au démarrage, on a lu le cahier des charges et inspecté le dossier (sans rien supposer). C'est pour ça que beaucoup de fichiers ont été ouverts au début : comprendre les règles avant de coder.
- **Une tranche verticale à la fois.** Chaque story contient tout : base, logique, écran, sécurité, tests. Jamais « toute l'interface d'abord, la base ensuite ».
- **Prouver, pas affirmer.** Une story n'est « faite » qu'après des tests exécutés. Pour la sécurité, on fait aussi une **contre-épreuve** : on casse volontairement une règle pour vérifier que les tests le détectent.
- **Un commit par story**, avec un message clair. Le journal `SUIVI_IMPLEMENTATION.md` garde les preuves.
- **Migrations, jamais de modification à la main.** Le schéma de la base n'évolue que par des fichiers SQL versionnés. `npm run db:reset` reconstruit tout de zéro : la base est reproductible.
- **Données fictives uniquement** (`@example.test`). Aucune donnée réelle de sportif dans le code.

## 7. La progression, étape par étape

### P0-01 : le socle (19/10)
Création de l'app Next.js avec TypeScript strict, Tailwind, ESLint, Prettier, et les commandes `lint`, `typecheck`, `check`. Node 24 (version stable à long terme) imposé par `.nvmrc`. Le squelette a été généré dans un dossier temporaire puis copié, pour **ne jamais écraser** le cahier des charges déjà présent.

### P0-02 : les environnements (19/10)
`.env.example` liste les variables nécessaires, sans valeurs. Les vraies clés vont dans `.env.local`, ignoré par Git. Un projet Supabase distinct par environnement (développement, test, production), pour ne jamais mélanger données de test et données réelles.

### P0-03 : la base reproductible (19/10)
Supabase local dans Docker, première migration (une fonction qui met à jour la date de modification), fichier de seed, commandes `db:start`, `db:reset`, `db:stop`. Vérifié : deux remises à zéro de suite sans erreur.

### P1-02 / P1-03 : organisations et isolation (19/10)
Trois tables : `organizations`, `organization_members` (qui appartient à quelle organisation, rôle propriétaire ou coach) et `platform_admins`. Règles RLS : chacun ne lit que sa propre organisation, personne n'écrit depuis le navigateur. Deux organisations de démo (A et B). **16 tests SQL** prouvent que A ne voit jamais B, et la contre-épreuve prouve que les tests détectent une fuite.

*Pourquoi avant la page de connexion ?* Parce que c'est le socle dont tout dépend. Il se teste sans interface.

### P1-01a : la connexion (19/10)
Page `/login`, déconnexion, espace `/coach` protégé. Le formulaire passe par une Server Action validée par Zod. Message d'erreur volontairement vague (« e-mail ou mot de passe incorrect ») pour ne pas révéler quels comptes existent. Les types TypeScript de la base sont **générés automatiquement** depuis le schéma (`npm run db:types`) : le code connaît exactement les colonnes.

### P1-04 : les garde-fous de rôle (20/10)
`requireCoach`, `requireOrgAccess`, `requirePlatformAdmin`, une page `/admin`, une page « Accès refusé », et l'aiguillage après connexion (coach vers `/coach`, admin vers `/admin`). Le statut d'admin est lu via une petite fonction SQL qui ne répond que pour l'utilisateur connecté. `requireAthlete` attendra que la table des sportifs existe : pas de faux garde-fou.

### Playwright : les tests navigateur (20/10)
Installé au moment où un vrai parcours existait. Chaque test tourne deux fois : écran d'ordinateur et écran de téléphone. Dès le premier passage, il a trouvé un vrai défaut (voir §8).

### P1-01b : mot de passe oublié (20/10)
Demande de lien, e-mail, lien à usage unique, nouveau mot de passe (10 caractères minimum). En local, les e-mails sont capturés par **Mailpit** (http://127.0.0.1:54324) au lieu d'être envoyés : le test Playwright lit l'e-mail via son API et fait tout le parcours. La destination du lien est dans une liste fermée, pour empêcher une redirection vers un site malveillant.

### Fiche sportif, début de P2-01 (20/10)
Avant de pouvoir inviter un sportif, il faut qu'il existe : on a donc créé la table `athlete_profiles` (nom obligatoire, e-mail et téléphone facultatifs, statut actif / en pause / archivé), la liste des sportifs et le formulaire d'ajout. Une fiche **n'est pas un compte** : le sportif n'a pas besoin de se connecter pour que le coach le suive, le lien avec un compte viendra avec l'invitation.

Trois choix de sécurité à retenir. L'**e-mail est unique par organisation** (le même sportif peut être suivi par deux coachs différents, mais pas apparaître deux fois chez le même). Un sportif **ne peut jamais changer d'organisation** : la base n'autorise la modification que de certains champs. Et l'adresse contient l'identifiant de l'organisation (`/coach/o/[orgId]/sportifs`) : c'est la première vraie utilisation de `requireOrgAccess`, testée en remplaçant l'identifiant par celui d'une autre organisation (« Accès refusé »). Ce type d'attaque s'appelle un **IDOR**.

Les champs restent volontairement minimaux : la fiche complète (objectifs, disponibilités, allures) attend la validation de Gianluca. On n'invente pas de règle métier.

### Invitation des sportifs, P1-05 (20/10)
Le coach clique sur « Inviter » à côté d'un sportif, génère un lien et le copie (un vrai bouton « Copier », testé). Il l'envoie lui-même par WhatsApp ou e-mail : pas de faux « message envoyé », les envois automatiques arriveront en P7. Le sportif ouvre le lien, choisit son mot de passe, coche « J'ai 18 ans ou plus » (les mineurs ne sont pas pris en charge pour l'instant), et arrive dans son espace `/app`, volontairement simple et honnête en attendant ses programmes.

Ce qui rend le lien sûr. Il contient 32 octets aléatoires, impossibles à deviner. La base ne stocke **que son empreinte** (hash SHA-256) : même si la base fuitait, aucun lien ne serait utilisable. Il expire après 7 jours, ne sert qu'une fois, et le coach peut le révoquer. Générer un nouveau lien annule l'ancien.

Comment le compte est créé. L'inscription libre est fermée, donc c'est le serveur qui crée le compte, avec la clé secrète, et uniquement pour l'e-mail inscrit sur la fiche par le coach. Puis une **fonction SQL unique et atomique** vérifie tout d'un coup (lien valide, non expiré, e-mail identique, âge confirmé) et relie la fiche au compte. « Atomique » veut dire : soit tout réussit, soit rien ne change.

Côté droits, un sportif ne lit que sa propre fiche et le nom de son organisation, et ne peut jamais entrer dans `/coach`. Après connexion, chacun arrive au bon endroit : coach, sportif ou administrateur. **Avec cette story, P1 (comptes et sécurité multi-coachs) est terminé.**

### Premier design system (« Athlix », orange), P0-05 (20/10)
Antonino a fourni son design system (« Sombre, précis, une seule couleur qui compte ») : graphite en base, orange `#FF5A1F` réservé à l'action, police Geist partout. On l'a traduit en **tokens** : des variables déclarées une seule fois dans `globals.css` (couleurs, rayons, tailles de texte). Les composants utilisent `bg-surface`, `text-muted` ou `bg-accent`, jamais une couleur en dur. Avantage : changer une teinte ou passer au thème clair se fait à un seul endroit.

On a aussi créé la **navigation** : barre latérale sur ordinateur, onglets en bas sur téléphone, avec seulement les sections qui existent vraiment (pas de faux liens). Le tableau de bord affiche de **vrais chiffres** calculés depuis la base, avec une seule carte orange par ligne comme le veut le design system. Pages d'erreur et 404 propres, sans jamais afficher de détail technique.

Méthode de vérification : les 27 tests Playwright ont confirmé que le changement de style ne cassait aucun parcours, puis des **captures d'écran automatiques** (ordinateur et téléphone) ont permis de repérer trois défauts visuels sur mobile, corrigés aussitôt. Le nom de marque est centralisé dans `src/config/brand.ts`. Une recherche a montré que « Athleex » est déjà un logiciel concurrent et qu'« Athlix » est utilisé ailleurs : Antonino a donc choisi **Coory**, appliqué en changeant une seule ligne. Le design system garde ses couleurs et sa police. Marque et nom de domaine à vérifier avant le lancement.

### Vitest et note de décision, fin de P0 (20/10)
Trois niveaux de tests désormais : **pgTAP** pour la base et la sécurité, **Vitest** pour les règles pures (11 tests en 0,3 seconde : validations de formulaires, jetons d'invitation), **Playwright** pour les parcours. La pyramide classique : beaucoup de petits tests rapides, quelques tests complets plus lents. On a aussi écrit une **ADR** (Architecture Decision Record, `docs/adr/0001`) : une page qui dit quelle stack on a choisie, ce qu'on a refusé et pourquoi. Tout nouvel outil devra passer par une ADR. C'est une pratique d'équipe professionnelle, utile en entretien.

### Fiche sportif, recherche et filtres, fin de P2-01 (20/10)
Chaque sportif a maintenant sa **fiche** : on y modifie le nom, le contact et le statut (actif, en pause, archivé) avec un **sélecteur segmenté** du design system. Archiver n'efface rien : le sportif quitte la liste active et peut être restauré. Une règle métier protège la cohérence : quand le sportif a activé son compte, son e-mail devient son identifiant de connexion, donc il n'est plus modifiable depuis la fiche (vérifié côté serveur, pas seulement grisé à l'écran).

La liste a une **recherche** et des **pastilles de filtre**. Choix technique : le filtre est **dans l'adresse** (`?statut=archives&q=camille`), pas dans la mémoire de la page. Avantages : on peut partager ou mettre en favori une liste filtrée, le bouton retour du navigateur fonctionne, et ça marche même sans JavaScript. Les valeurs lues dans l'adresse sont validées par Zod : une adresse bricolée retombe sur des valeurs sûres.

Leçon de test du jour : deux tests lancés **en parallèle** ont créé des sportifs à la même milliseconde, donc avec le même nom « unique ». On ajoute maintenant une partie aléatoire aux noms de test.

### Repères datés et premier module de domaine, P2-03 (20/10)
Chaque sportif peut avoir ses **repères** : allures (endurance, seuil, 5 km… y compris une plage comme `6:40–7:15`), fréquence cardiaque, charges de référence. Chaque mesure est **datée** et l'historique est **immuable** : une nouvelle valeur ne remplace pas l'ancienne, elle s'ajoute ; la plus récente fait foi. La base interdit même la modification d'une mesure (on supprime une erreur puis on ressaisit). Pourquoi ? Parce que les programmes déjà publiés doivent garder les allures de leur époque.

C'est aussi le premier code dans `src/domain/` : la lecture et l'écriture des allures (`4:55` ↔ 295 secondes par km, vitesse en km/h). Ce sont des **règles pures**, sans base de données ni écran, donc faciles à tester (19 tests en quelques millisecondes). Une saisie ambiguë comme `4:5` est refusée avec une explication plutôt que devinée : en sport, une allure mal interprétée, c'est une séance mal dosée.

Piège découvert : avec React 19, un formulaire relié à une action **se vide après chaque envoi, même en cas d'erreur**. Le coach aurait perdu sa saisie au moindre faute de frappe. Les actions renvoient maintenant ce qui a été saisi, et un test vérifie que la saisie reste affichée.

### Calcul des allures depuis un test (20/10)
Décision du coach : les allures se déterminent par un **test de Cooper** (distance maximale en 12 minutes) ou un **test de 5 km**. On en déduit la **VMA** (vitesse maximale aérobie) : distance ÷ 200 pour Cooper, vitesse du 5 km ÷ 95 % pour le 5 km. Chaque allure est ensuite un **pourcentage de la VMA** (endurance 65–75 %, marathon 80 %, seuil 85 %, 10 km 90 %, 5 km 95 %).

Trois choix à savoir expliquer. **Le calcul propose, le coach décide** : il voit l'aperçu en direct, décoche ce qu'il ne veut pas, puis valide. **Le serveur refait le calcul** à partir du résultat brut du test : il ne fait jamais confiance aux chiffres envoyés par le navigateur. Et **la même fonction** sert à l'aperçu (dans le navigateur) et à l'enregistrement (sur le serveur) : c'est l'intérêt d'avoir mis ces règles dans `src/domain/`, sans dépendance à la base. Chaque allure enregistrée garde une note qui dit d'où elle vient.

### Disponibilités et données de santé avec accord (22/10)

Ce sont des **données de santé**, protégées par l'article 9 du RGPD : on ne peut les noter qu'avec l'**accord explicite** de la personne. Antonino a choisi que cet accord puisse venir de deux côtés : du sportif lui-même, depuis son espace (« J'accepte »), ou du coach qui note l'accord reçu en précisant comment (oral, écrit, formulaire signé).

Ce qui rend la règle solide, c'est qu'elle est garantie **par la base**, pas par l'écran. Une contrainte de la table refuse tout texte de santé sans accord en cours. La date d'accord ne peut être écrite par personne directement : seulement par deux **fonctions** en base qui vérifient qui appelle (le sportif concerné ou un coach de son organisation), puis écrivent la fiche et le **journal** dans la même transaction. Le journal ne se modifie jamais : on y ajoute seulement « accord donné » ou « accord retiré », avec la date et qui l'a fait. C'est ce qu'on appelle une **piste d'audit**. Retirer l'accord **efface** ce qui avait été noté, et le sportif voit toujours ce que son coach a écrit sur lui.

Les 21 tests SQL de cette partie essaient justement de contourner la règle : écrire la date d'accord à la main, écrire dans le journal, donner l'accord pour quelqu'un d'autre, depuis une autre organisation, sans être connecté. Tout est refusé.

Étape 2 : les **coquilles de navigation**. Trois espaces partagent le même cadre (`AppShell`) : une barre latérale sur ordinateur, et sur téléphone une barre du haut avec le titre de la page au centre, plus un menu hamburger (coach, admin) ou une barre d'onglets en bas (sportif, pour atteindre sa séance du jour en deux gestes). Le titre de la barre du haut se déduit de l'adresse de la page : le cadre n'a pas besoin que chaque page le lui dise. Les modules pas encore construits ont désormais leur vraie adresse (`/coach/programmes`…) et une page vide honnête : quand un module sera construit, seule sa page changera, pas le menu. Piège rencontré : en Tailwind, une taille de texte nommée « page » se confondait avec la couleur « page » ; la classe `text-page` peignait le titre en bleu nuit sur fond bleu nuit. Renommée `text-heading`.

Retouche demandée par Antonino après l'étape 2 : le **thème clair devient le défaut**. Plutôt que de poser un attribut sur chaque page, les couleurs claires sont maintenant celles de `:root`, et le sombre s'active par `data-theme="dark"`. Le bloc sombre est écrit après le bloc clair : à spécificité égale, c'est le dernier qui gagne. Sur la connexion, une carte de marque n'apparaît que sur téléphone ; pour centrer le formulaire sans toucher aux autres pages, la page se signale par un attribut (`data-mobile-fill`) et la coquille ne lui donne toute la hauteur que si elle le trouve (`:has()`). Des captures avant / après comparées pixel par pixel ont prouvé que l'inscription n'avait pas bougé.

Étape 3 : les **pages d'entrée**. La logique ne bouge pas, mais chaque action renvoie maintenant une erreur par champ, pour l'afficher sous le bon champ comme le prototype. Nouveauté : la page « Vérifie ta boîte mail ». Pour y afficher l'adresse sans la mettre dans l'URL (elle finirait dans l'historique et les journaux), l'inscription la range dans un cookie illisible par le navigateur (httpOnly) pendant une heure, la durée du lien. La page « Bienvenue » montre l'écran du prototype quand l'inscription par e-mail a déjà tout fourni ; un clic crée l'espace. Piège rencontré : le serveur de développement servait encore l'ancien cadre des pages d'accès malgré le bon fichier ; la vérification s'est faite sur la version de production, qui était juste.

Étape 4a, première partie : un **tableau de bord vivant et un agenda qu'on manipule**, retouchés en direct avec Antonino. Il voulait voir des tâches et des messages dans les cartes du haut ; plutôt que d'inventer des chiffres dans le code, on a créé les **vraies tables** (tâches, messages, suivi des factures), protégées par organisation comme le reste, et seul le **jeu de démo** les remplit. Une tâche se coche d'un rond, comme dans l'app Rappels de l'iPhone : l'écran change tout de suite (`useOptimistic` de React), le serveur enregistre, et si l'enregistrement échoue, le rond revient seul. Qui a coché la tâche est écrit par la base elle-même, jamais envoyé par le navigateur. Ouvrir une conversation marque ses messages lus, mais seulement **après** l'affichage, dans le navigateur : un simple préchargement de la page ne doit rien marquer.

L'agenda est devenu interactif. Un clic sur un créneau vide ouvre la fenêtre « Nouvelle séance » au bon jour et à la bonne heure, et c'est **la même fenêtre partout** (tableau de bord, Agenda, Séances), montée une seule fois dans la coquille de l'espace coach. Une séance se **glisse** à la souris ou, sur téléphone, après un appui long (sinon le doigt ne pourrait plus faire défiler les jours). Le vrai problème était métier : déplacer « Piste du mercredi », c'est déplacer une date ou toute la série ? On demande à chaque fois. Une date seule devient une ligne d'**exception** (date d'origine, nouvelle place), et toute la série se décale avec ses exceptions dans **une seule fonction SQL**, donc en une transaction : jamais une série à moitié déplacée. Le calcul des dates d'une séance est centralisé dans une fonction pure, testée, utilisée par la grille, les listes et la fiche. Enfin, un **nouveau sportif** se crée depuis la fenêtre même : on tape son nom, sa fiche minimale existe aussitôt dans Sportifs et la séance lui est rattachée. Une première version laissait la séance « sans sportif » en attendant ; Antonino a préféré la fiche tout de suite, plus simple : la règle « une séance individuelle a toujours son sportif » est revenue, par une nouvelle migration qui n'a rien perdu. Une icône signale les fiches **à compléter** (sans nom de famille, ou sans moyen de contact) ; ce n'est pas une case cochée en base mais un calcul, donc le repère disparaît tout seul dès que la fiche est complète.

Premier retour du coach lui-même (D-36) : il ne savait pas combien il gagnait par semaine. La vraie question était « qu'est-ce qui compte comme chiffre d'affaires ? ». Réponse : l'**argent reçu**, le jour où il est reçu (un forfait de 3 000 € payé d'avance compte ce jour-là). On a donc créé une table des **paiements reçus**, sans se lancer tout de suite dans les forfaits. Le coach note le montant **TVA comprise** (c'est ce qu'il a en main) et le taux ; le HTVA et la TVA se calculent, en centimes entiers pour ne jamais perdre un centime d'arrondi (HTVA arrondi, TVA = le reste, donc le total tombe toujours juste). Le mode de paiement sépare ce qui arrive sur le compte bancaire (virement, Bancontact) du reste. Les messages non lus quittent les grandes cartes pour une **pastille rouge**, comme sur l'iPhone, sur l'entrée Messages et la cloche.

Antonino a repéré une incohérence : la cloche affichait « 3 », mais la page Notifications était vide. La page est devenue réelle, rangée en sections (messages non lus, tâches du jour ou en retard, factures en retard, fiches à compléter). Il n'y a **pas de table des notifications** : chaque section est une requête sur les données existantes, donc une notification disparaît d'elle-même quand la chose est faite, et elle ne peut jamais être « en retard » sur la réalité.

Derniers réglages du cadre (D-38) : le menu de gauche gagne « Assistant IA » et « Notifications », et la carte de la personne devient un **menu du compte** (Mon profil, Paramètres, Changer de compte, Thème, Se déconnecter), dessiné d'après une maquette d'Antonino. Le thème accepte maintenant « Système » : le petit script lancé avant l'affichage suit le réglage de l'appareil, même s'il change pendant la visite. Piège rencontré : un menu qui doit déborder d'une barre latérale qui défile est coupé par celle-ci ; il est donc positionné par rapport à l'écran (position fixe), calculée sur la carte au moment de l'ouverture.

Côté outils de développement, deux causes faisaient sans cesse déconnecter Antonino : « Se déconnecter » fermait toutes les sessions du compte (les tests, connectés avec le même compte, le déconnectaient aussi), et chaque remise à zéro de la base effaçait les sessions. La déconnexion ne ferme plus que l'appareil, comme partout, et `npm run db:reset` garde les sessions récentes et le profil du développeur. Ce script a lui-même eu un défaut instructif : enchaîné par `&&`, il ne restaurait rien quand le reset échouait, et la sauvegarde suivante écrasait la bonne copie. Il restaure maintenant toujours, et une sauvegarde ne recule jamais.

Étape 4a, deuxième partie : la **liste des sportifs**. Antonino a remplacé les libellés d'accès (« Compte activé », « Invitation en attente », « Sans compte ») par des signes plus discrets : une petite icône message, qui ouvre directement la conversation, et un fond vert très doux pour un compte activé ; une petite icône pour une invitation envoyée ; rien du tout sans compte, seulement le bouton « Inviter ». Les chiffres du haut (actifs, en pause, compétitions à venir, fiches à compléter) sont calculés sur la même lecture que la liste, et les filtres sont dans l'adresse (`?statut=`, `?discipline=`) : un filtre se partage et survit au rechargement. Leçon de test : une icône dont le nom accessible contient « Nom de famille » entrait en collision avec le champ du même nom dans les tests ; le texte caché aux yeux (sr-only) plus une infobulle évitent ce piège.

Puis Antonino a dessiné la liste qu'il voulait : un **tableau** où le statut et le type de programme se changent d'un appui sur leur pastille, plus des cases à cocher pour agir sur plusieurs sportifs à la fois. Question de fond : le « type de programme » était jusque-là **déduit** de l'objectif principal. Pour qu'un sportif qui a fini son Hyrox repasse en Hybride sans toucher à ses objectifs, c'est devenu un **vrai champ** de la fiche, par une nouvelle migration, avec son test SQL (le coach le change pour ses sportifs, jamais pour ceux d'une autre organisation, et le sportif ne le change pas lui-même). Une seule action serveur sert à la fois pour une ligne et pour une sélection : la liste d'identifiants vient du navigateur, donc elle est validée (Zod) et la mise à jour est limitée à l'organisation du coach. Sur téléphone, le tableau devient une carte par sportif : les mêmes cellules, rangées autrement par la grille CSS (`display: contents` sur ordinateur). Piège de test : un texte caché « Sélectionner Thomas Peeters » pour la case à cocher faisait trouver deux fois « Thomas Peeters » ; le nom est passé sur la case elle-même (`aria-label`).

Retouches du 26/10, sur le vrai téléphone d'Antonino. D'abord un piège de développement : le bouton « œil » du mot de passe ne répondait pas. Le bouton n'était pas en cause : ouvert par l'adresse du Mac sur le Wi-Fi, Next 16 bloque par sécurité le JavaScript en développement ; la page s'affichait et la connexion marchait (un formulaire fonctionne sans JavaScript), mais rien d'interactif. Une ligne de configuration autorise le réseau de la maison. Ensuite, trois retouches : sur téléphone, les filtres deviennent deux boutons qui montrent le choix en cours et ouvrent la liste des choix, au lieu de rangées de pastilles qui passent à la ligne ; la vue d'ensemble de la fiche sépare chaque information par un filet, libellé au-dessus, valeur en dessous, comme le prototype ; et un objectif se **modifie** enfin. Côté base, la règle était volontaire (« pour corriger : supprimer puis recréer ») : une migration ouvre la modification des seuls champs de saisie, jamais le sportif ou l'organisation, et le test SQL le vérifie. La fenêtre de modification réutilise exactement les champs de l'ajout : une seule source de règles.

Le même jour, un **audit** du tableau de bord et des sportifs face au prompt Claude Design a confirmé l'ordre de travail et fait ressortir ce qui manquait à la fiche. Elle gagne le bouton rouge « Créer un programme » : créer un programme depuis un sportif est, pour Antonino, le cœur de l'application. En attendant le module, le bouton mène à la page Programmes. Elle gagne aussi un menu « ••• » identique à celui de la liste, une carte « Prochaines séances » (réutilisant le calcul de l'agenda, déjà testé, filtré sur le sportif) et un « temps visé » sur les objectifs. Leçon : une carte d'une grille CSS sans colonnes déclarées prend la largeur de son plus long texte sur une ligne ; `grid-cols-1` (une colonne de largeur `minmax(0, 1fr)`) la ramène à celle de l'écran.

Puis le **cœur** : les programmes. Antonino a montré le tableur de Gianluca et ses maquettes : une ligne par semaine, des séances numérotées, **sans jour** (le sportif les place quand il veut). Le cahier des charges avait déjà prévu la bonne structure : un programme, des **versions publiées figées** (le sportif suit toujours une version précise, que le coach ne peut pas modifier en douce), et une ligne par séance publiée, repérée par sa semaine et son numéro ; c'est cette ligne que les retours du sportif viseront. Le contenu d'une séance est un **objet structuré** (étapes, bloc « Répéter 4 fois », conseils), vérifié à chaque lecture : une donnée mal formée est écartée plutôt qu'affichée de travers. On a commencé par l'**affichage**, avec un programme de démo inventé de 12 semaines, pour valider la forme avant de construire l'éditeur, qui est la partie la plus délicate. Les tables sont en lecture seule depuis le navigateur tant que la publication contrôlée n'existe pas.

Deux leçons. Une zone de message toujours présente avec `role="status"` se confond avec les messages de statut des formulaires : les tests qui cherchaient « le » statut en trouvaient deux. Et le serveur de développement peut garder une ancienne version d'un module : une constante nouvellement exportée arrivait `undefined` ; la déplacer dans un nouveau fichier a suffi.

En fin de journée, le **tableau de bord** a été recentré sur ce que Gianluca doit voir en premier : ses tâches et l'argent encaissé dans la semaine. Les chiffres de l'agenda (coachings du jour, heures de la semaine) descendent sous le calendrier, en petites tuiles colorées. Ces tuiles existaient déjà sur la page Agenda, écrites directement dans la page : elles deviennent un composant partagé (`StatTiles`), pour que les deux pages gardent le même style sans copier le code. La vue « Aujourd'hui » de la page Agenda reprend la grille horaire du tableau de bord au lieu d'une liste. Leçon d'accessibilité : quand le libellé complet d'une carte est masqué sur téléphone au profit d'un titre court, le lien perd son nom pour les lecteurs d'écran ; un `aria-label` complet le lui rend, et les tests qui cherchaient la carte par son nom l'ont signalé aussitôt.

Dernier chantier du jour : **le prix des séances**. Antonino voulait, où qu'une séance soit créée, un prix, une case TVA et le mode (espèces ou virement), reliés à la carte « Encaissé cette semaine ». Le choix important : une séance avec un prix n'est **pas** de l'argent reçu. On garde la règle de la comptabilité (l'encaissé, c'est ce qui est vraiment arrivé) et on relie les deux : sur la page de la séance, chaque date se « marque payée », ce qui crée un vrai paiement reçu, daté du jour, avec le montant, la TVA et le mode de la séance, calculés par le serveur, jamais envoyés par le navigateur. Un index unique en base garantit qu'une date ne se paie qu'une fois, même en cliquant deux fois. Puis deux retours de Gianluca ont affiné le modèle. D'abord, certains sportifs paient **trois mois d'avance** : un paiement peut couvrir une période, il compte en entier la semaine où il est reçu, et les dates du sportif dans la période se montrent « comprises dans le forfait ». Ensuite, sa façon de compter : **facturé par virement = prix hors TVA, la TVA s'ajoute** (65 € deviennent 78,65 €) ; **en espèces = prix direct**. Plutôt que deux prix, le formulaire garde un seul prix et une case « TVA comprise » que le mode choisi règle tout seul, modifiable. Leçon : les règles d'un métier arrivent par petites phrases, après coup ; un modèle simple (un prix, un mode, une case) les absorbe sans tout refaire.

### Le nouveau sportif, en une seule page (28/10)
La page « Nouveau sportif » ne demandait que le nom et le contact ; tout le reste se remplissait ensuite onglet par onglet. Elle reçoit maintenant la fiche complète en une fois : profil, objectif principal, disponibilités, et une carte « Accord santé ». Le choix important : **ne rien réécrire**. Les champs des onglets Profil et Disponibilités ont été sortis dans des composants partagés, et la lecture du formulaire réutilise les règles déjà testées (fiche, disponibilités, objectifs, accord). Un sportif créé ici est donc exactement celui qu'on aurait obtenu onglet par onglet. L'accord santé suit la même voie que sur la fiche : une fonction SQL qui vérifie qui appelle et journalise l'accord, et la base refuse toute contrainte physique sans accord en cours. Leçon de test : Next 16 garde la page quittée cachée dans le DOM ; avec un formulaire plus riche, des libellés comme « Domicile » existaient deux fois. Les tests ciblent donc les éléments visibles, ou passent par le rôle (case à cocher, liste déroulante), qui ignore les éléments cachés.

### L'audit du mouvement, façon Apple (28/10)
Un audit fondé sur les conférences de design d'Apple a fait ressortir ce qui séparait Coory d'une « vraie » app : les fenêtres apparaissaient d'un coup. Elles montent maintenant du bas avec un **ressort** : pas une durée fixe, mais un mouvement qui part de la vitesse du doigt quand on lâche la fenêtre après l'avoir glissée. Le navigateur sait animer une courbe décrite point par point (`linear()`) : on calcule cette courbe à partir de la physique d'un ressort, sans bibliothèque. Deux leçons. D'abord, **ne jamais bloquer l'interface pendant une animation** : une fenêtre qui se ferme en glissant restait « modale » quelques dixièmes de seconde, et la page ne répondait pas. La vraie fenêtre se ferme désormais tout de suite, et c'est une copie visuelle, inerte, qui joue la sortie. Ensuite, les tests automatiques ont trouvé deux vrais défauts de geste : le relâcher d'un glissé passait pour un clic sur le fond, et un message d'erreur qui apparaît pendant l'appui faisait bouger le bouton sous le doigt.

### La case Notes et les données de santé (28/10)
Antonino voulait une case où Gianluca note les blessures, et une autre où il écrit ce qu'il veut. Le piège : mettre les deux dans le même champ. Une blessure est une **donnée de santé**, que le RGPD protège plus fort que le reste : on ne la garde qu'avec l'accord explicite du sportif. Une préférence (« n'aime pas courir le matin ») n'en est pas une. Deux cases donc : « Blessures et points d'attention », qui n'apparaît qu'avec l'accord et que la base refuse sans lui, et « Notes libres », privées entre coachs. Le champ santé quitte l'onglet Disponibilités et s'enregistre par sa propre action : modifier ses horaires ne peut plus effacer une blessure par accident. Leçon : la bonne structure de données vient parfois d'une règle juridique, pas d'un besoin d'écran.

### Des Paramètres de vraie app (28/10)
Pour faire des Paramètres « comme une vraie app », on a regardé ce que proposent les outils de coaching et de facturation, et gardé cinq sections : Profil, Préférences, Facturation et légal, Sécurité, Données. Le choix important : **chaque réglage fait vraiment quelque chose**. La durée, le lieu, le prix et le mode proposés d'office préremplissent la fenêtre « Nouvelle séance » ; les heures de l'agenda règlent les grilles ; les interrupteurs de la cloche changent son compteur et la page Notifications. Un réglage qui ne change rien serait un faux écran. Côté légal, Gianluca a deux structures (son activité d'indépendant et l'ASBL) : on en enregistre plusieurs, avec des numéros **vérifiés par leur clé de contrôle** (le numéro d'entreprise belge et l'IBAN se vérifient par un calcul modulo 97), ce qui attrape une faute de frappe avant qu'elle n'arrive sur une facture. Côté sécurité, changer de mot de passe redemande l'actuel, et l'export JSON donne toutes les données de l'organisation, comme le RGPD le prévoit. La suppression complète d'un compte est volontairement repoussée : il faut d'abord décider quoi faire des sportifs liés et de leurs photos.

### Les Paramètres en fenêtre, comme Claude.ai (28/10)
Antonino n'aimait pas la page des Paramètres : on quittait ce qu'on faisait pour y aller. Il voulait qu'un clic sur son nom, puis « Paramètres », ouvre une grande fenêtre par-dessus la page, comme les réglages de Claude.ai. Première piste, les **routes interceptées** de Next.js (l'adresse change, mais la page reste derrière) : le routage strict de Next 16 l'a refusée (page de connexion en 404, puis deux routes jugées identiques). On a donc choisi plus simple : un **contexte React** qui ouvre la fenêtre et charge les données à l'ouverture, par une action serveur qui revérifie qui demande. Le contenu est un seul composant, partagé entre la fenêtre et la page complète, qui reste pour un lien direct. Leçon technique : un fichier marqué `"use client"` ne doit exporter que des composants ; la liste des sections, exportée depuis ce fichier et lue par une page serveur, arrivait sous forme de « référence client » et faisait planter la page (`SECTIONS.find is not a function`). Elle vit maintenant dans un petit module neutre que les deux côtés lisent.

### Les outils, tranche 1 : des tâches qu'on gère vraiment (28/10)
Les tâches se cochaient, mais on ne pouvait ni en créer, ni en corriger, ni en supprimer. Le choix : une seule fenêtre « tâche », montée une fois pour toutes les pages coach, comme « Nouvelle séance ». Elle s'ouvre vide pour créer, ou remplie quand on touche le titre d'une tâche, et la suppression passe par une confirmation. Les règles du formulaire sont écrites une fois (Zod) et la base les répète (contraintes, droits par colonne) : le navigateur ne peut pas glisser une catégorie inventée ni changer l'organisation d'une tâche. Leçon d'écran : sur téléphone, mettre les pastilles à droite du titre le coupait au bout de quelques mots ; on les a passées dessous, et le titre tient sur deux lignes.

### Les outils, tranche 2 : des documents privés (28/10)
Pour les documents, la question n'était pas l'écran mais la confiance : un contrat ou une facture ne doit jamais être lisible par un autre coach. On a repris le modèle des photos : un espace de stockage **privé**, rangé par dossier d'organisation, avec des règles RLS sur les fichiers eux-mêmes, et une route de l'app qui sert le fichier avec la session de la personne. Une autre organisation reçoit un 404, comme si le document n'existait pas. Deux précautions de plus : le format est lu dans les premiers octets du fichier (un texte renommé en .pdf est refusé), et le chemin de stockage est tiré au hasard, jamais le nom envoyé par le navigateur. Leçon d'écran : l'envoi se fait « à la main » plutôt que par l'action automatique du formulaire, car React vide le formulaire après l'envoi ; en cas d'erreur, le fichier choisi et les champs restent en place.

### Les outils, tranche 3 : lire et masquer des notifications calculées (28/10)
Les notifications de Coory ne sont pas stockées : elles sont calculées à partir des vraies données (une tâche en retard, une facture impayée). Comment alors en « lire » une ? On garde seulement l'état choisi par le coach, rangé sous une **clé** qui décrit la situation : « cette tâche, avec cette échéance ». Si la tâche est reportée, la clé change, et la notification revient non lue, ce qui est le comportement attendu. Chaque coach a ses propres états (lire n'efface rien pour un collègue). Leçon de test : un test qui compte la cloche du coach A échouait au hasard, parce qu'un autre test créait en même temps des compétitions pour ce même coach. Le test tourne maintenant avec le coach B, en série, et remet tout en place à la fin.

### Les outils, tranche 4 : une recherche qui ne fait pas confiance à la saisie (28/10)
La recherche globale interroge cinq tables à la fois et range les résultats par groupe pendant qu'on tape. Le point délicat : ce que le coach tape finit dans une requête SQL de type « contient ». Les caractères spéciaux de cette requête (`%`, `_`) sont donc échappés, et ceux qui servent à combiner des filtres (virgules, parenthèses) deviennent des espaces : taper « %% » ne renvoie pas toute la base, et un test le vérifie. Comme partout, l'action revérifie l'organisation et la RLS fait le reste : le document d'un autre coach ne sort jamais. Côté écran, seule la dernière réponse compte : si une recherche lente arrive après une plus récente, elle est ignorée. Leçon : un état React ne se met pas à jour dans un effet ; la recherche part du gestionnaire de saisie, ce qui est aussi plus simple à lire.

### Le design « Graphite & Or », sans toucher à l'architecture (29/10)
Antonino a fourni un nouveau design system et des images de référence. Consigne : changer **le style seul**, pas la structure ni les fonctionnalités. Les **tokens** ont tout rendu possible : couleurs, polices et rayons sont déclarés à un seul endroit (`tokens.css`, `globals.css`), donc la plupart des écrans ont changé sans être ouverts. La palette des disciplines a été recalculée en **OKLCH**, un espace de couleur où la luminosité est fiable : toutes les couleurs ont la même clarté et seule la teinte change, d'où un ensemble qui « va ensemble », lisible en sombre comme en clair. Chaque couleur a un rôle fixe : l'or pour l'action, le rouge pour les erreurs et les suppressions, l'orange pour les retards.

Trois petites mécaniques méritent d'être expliquées. Le **menu repliable** retient son état dans le navigateur, et un script lu avant l'affichage évite que le menu « saute » au chargement (comme pour le thème). La **flèche retour** se souvient de la page précédente et de son titre (dans `sessionStorage`, propre à l'onglet) : ouverte depuis le tableau de bord, une séance ramène au tableau de bord et l'annonce. On ne se sert pas du « précédent » du navigateur, car les onglets d'une fiche ajoutent des étapes à l'historique. L'**agenda sur 24 h** garde une grille complète mais n'en montre que la plage choisie dans les Paramètres, et défile dans sa carte. Leçon de test : les tests du glisser-déposer calculaient la position d'une heure à partir d'une grille de 6 h à 22 h ; ils ont été adaptés, et c'est exactement le genre de casse qu'on veut voir arriver dans un test plutôt que chez le coach.

### Une page de moins : la vue Liste de l'Agenda (29/10)
La page Séances montrait les mêmes séances que l'Agenda, sous une autre forme : deux endroits pour une seule information, c'est deux endroits à maintenir et un coach qui se demande où regarder. Elle devient une **vue de l'Agenda**, à côté de Semaine et Mois, comme le « Planning » de Google Agenda. Rien ne change en base : la vue lit les mêmes séances avec le même garde-fou. La liste par jour du tableau de bord a été sortie dans un **composant partagé**, pour que les deux écrans restent identiques sans copier le code. Supprimer une page, c'est aussi retirer son entrée de menu, son module et les liens qui y menaient : un test vérifie maintenant que « Voir tout » arrive bien sur la vue Liste.

### Des factures qu'on ne peut plus trafiquer (29/10)
Une facture est un document légal : une fois envoyée, elle ne doit plus changer, et les numéros doivent se suivre sans trou. On l'a donc modélisée en deux états : un **brouillon** qu'on corrige librement, puis une facture **émise**, figée. Le numéro n'est pas calculé dans l'application mais **par la base**, dans une fonction SQL qui verrouille un compteur par structure et par année : si deux clics « Émettre » arrivent en même temps, l'un attend l'autre, et si l'émission échoue, le numéro n'est pas consommé (tout est dans la même transaction). Même un développeur qui contournerait l'écran ne pourrait pas modifier une facture émise : un **trigger** l'interdit en base, et un test pgTAP le prouve hors RLS. La facture garde aussi une **copie** de la structure (raison sociale, TVA, IBAN) au moment de l'émission : changer d'adresse plus tard ne réécrit pas les anciennes factures.

Le PDF est fabriqué avec **React-PDF** (note de décision ADR 0002) : la facture s'écrit en composants React, rendue sur le serveur sans navigateur. Il a été choisi parmi trois options parce qu'il reste léger et marche chez n'importe quel hébergeur ; il servira aussi aux programmes. Côté métier, deux règles de Gianluca se retrouvent dans le code : seuls les virements se facturent, et une facture « déjà payée » crée aussi le **vrai paiement** dans la Comptabilité, pour que le chiffre d'affaires reste juste.

### Une app pour tous les pays : Coory ne joue pas au juriste (29/10)
Première version des factures : des phrases légales belges écrites dans le code (« régime de franchise… »), et une liste de points « à faire valider par un comptable ». Antonino a pointé le problème : si Coory sert un jour en France ou ailleurs, l'app ne peut pas connaître les lois de chaque pays. La décision (D-66) : Coory fournit des **outils neutres** (numéro qui se suit, structure, TVA au choix, mentions libres, PDF) et le coach reste responsable de ce qu'il écrit. Techniquement, c'est surtout du code en moins : les phrases en dur ont disparu, et le PDF imprime les mentions saisies par le coach. Même logique pour les espèces : plutôt que d'imposer la règle d'un seul coach, un **réglage** laisse chacun choisir s'il veut les voir dans « À facturer ».

### Des catégories que le coach choisit lui-même (29/10)
Les Documents avaient cinq catégories fixes, écrites dans le code et dans une contrainte de la base. Pour que chaque coach range à sa façon, la catégorie est devenue une **table** : chaque organisation a ses propres catégories, et un document pointe vers l'une d'elles. Trois détails comptent. Une **clé étrangère composée** (identifiant + organisation) empêche un document de pointer vers la catégorie d'un autre coach, même en contournant l'écran. Supprimer une catégorie ne supprime pas ses documents : la base remet simplement leur catégorie à vide (`ON DELETE SET NULL`). Et un **trigger** donne les cinq catégories de départ à chaque nouvelle organisation, pour qu'un nouveau coach ne commence pas devant une liste vide. La migration a converti les documents existants : rien ne s'est perdu en route.

Sur les factures, le coach saisit maintenant son prix **hors TVA** (c'est ainsi que Gianluca raisonne : 65 € HTVA) et voit la TVA s'ajouter en direct. Avant de changer, on a vérifié par un petit script que passer du HTVA au TVAC puis revenir ne perd jamais un centime (un million de montants testés pour chaque taux) : on peut donc garder un seul montant en base sans risque d'écart.

### Une app vendable hors de Belgique (29/10)
Jusqu'ici, l'euro et la TVA belge (21, 12, 6, 0 %) étaient écrits partout. Pour vendre Coory ailleurs, trois idées. **Le taux de TVA devient libre** : plutôt que de tenir une liste de taux pour chaque pays (et de la suivre à chaque changement de loi), le coach écrit le sien une fois dans sa structure, et Coory le propose sur chaque facture. Les calculs se font en **nombres entiers** (8,1 % devient 810 centièmes de point) : en JavaScript, 0,1 + 0,2 ne fait pas exactement 0,3, et un centime perdu sur une facture, ça se voit. **Chaque montant garde sa devise** : un paiement reçu en euros reste en euros, même si le coach déménage en Suisse ; c'est la base (un trigger) qui pose la devise, jamais le navigateur. Et le **pays décide des formats** : le contrôle du numéro belge ne s'applique qu'à une structure belge.

L'inscription demande tout cela tout de suite (pays deviné d'après la langue du navigateur, devise proposée d'après le pays), mais la TVA peut attendre : un coach qui ne facture pas avec Coory utilise quand même l'agenda et les programmes. Détail appris en route : dans une fonction SQL `SECURITY DEFINER`, `current_user` est le propriétaire de la fonction, pas la personne qui l'appelle ; le trigger de devise est donc en `SECURITY INVOKER` pour savoir qui écrit. Autre détail : les noms des pays sont **figés dans un fichier** plutôt que calculés à la volée, pour que le serveur et chaque navigateur affichent exactement le même texte. Les icônes des documents ont aussi pris la **couleur de leur catégorie** (Facture en or, Bilan en bleu), choisie dans une palette fermée de jetons du design system.

### Déménager sans fausser l'historique (29/10)
Un coach qui passe de la Belgique à la Suisse change de devise. Tout convertir aurait été simple, mais faux : un paiement reçu en euros a vraiment été reçu en euros, il figure ainsi sur le relevé bancaire, et une facture émise ne se modifie plus. On a donc séparé le **passé** (gardé dans sa devise) du **futur** (converti au taux que le coach saisit). Tout se fait dans **une seule fonction SQL**, en une transaction : si une étape échoue, rien ne change. Chaque changement est **gardé dans un historique** ; il sert ensuite à afficher un total « ≈ » quand une période mélange deux devises, avec le détail (« 121,00 € + 108,10 CHF »). Le convertisseur sait suivre une chaîne de déménagements (EUR puis CHF puis GBP). On n'a pas branché de service de change en ligne : une dépendance externe de plus pour un cas rare, et le coach connaît le taux de sa banque.

### Un graphique qu'on peut croire, et une couleur de sélection (29/10)
La Comptabilité a gagné un graphique circulaire et un vrai tableau (période par période, mode de paiement par mode). Pour les couleurs du graphique, on n'a pas choisi « à l'œil » : un petit script vérifie qu'aucune paire de parts voisines ne se confond, y compris pour les daltoniens, en sombre comme en clair. Le premier choix (les couleurs des disciplines) a échoué au test : le bleu et le violet étaient presque identiques pour un daltonien. Dans un anneau, seules les parts voisines se touchent : on a donc placé les deux couleurs proches face à face. Et la couleur n'est jamais seule : chaque part a son montant écrit dans la légende, et le tableau donne tous les chiffres. Côté calcul, tout est une fonction pure testée (périodes, sommes par mode, TVA), y compris après un changement de devise.

Autre leçon, sur le jaune de sélection : un or légèrement transparent posé sur un fond presque noir donne du brun, c'est mécanique (on mélange du jaune avec du noir). On a comparé plusieurs teintes côte à côte avant de choisir un jaune citron plus franc. Et quand Antonino a vu un contour blanc au lieu du jaune, la cause était un serveur de développement qui servait l'ancienne feuille de style : une bordure sans couleur connue prend la couleur du texte.

### Les dépenses, le résultat, et une page en widgets (29/10)
La Comptabilité sait maintenant ce que le coach dépense, et donc ce qu'il gagne vraiment. Deux idées. Une dépense qui revient (le loyer) n'est écrite **qu'une fois**, avec « chaque mois » : le calcul la fait compter chaque mois (un 31 compte le 28 février), et « Arrêter » lui donne une date de fin sans effacer le passé. Et le résultat suit le **statut TVA** : pour un coach soumis à la TVA, la TVA n'est pas à lui (il la reverse ou la récupère), donc on compare gagné HTVA et dépensé HTVA. Le changement de devise a dû apprendre à **couper** une dépense mensuelle en cours : la partie passée reste en euros, une copie convertie reprend à la prochaine date.

Côté mise en page, chaque rangée de widgets a la même hauteur. L'astuce vient du tableau de bord : la colonne de droite est posée « par-dessus » sa case (position absolue), si bien que c'est le tableau de gauche qui décide de la hauteur, et la liste de droite défile à l'intérieur. Enfin, l'en-tête de toutes les pages a été unifié ; un piège rencontré : une icône est une fonction, et une fonction ne peut pas être envoyée d'un composant serveur à un composant du navigateur. L'icône imposée est donc dessinée côté serveur.
### La bibliothèque d'exercices : préparer les données avant de coder (30/10)
Avant d'écrire une ligne de l'application, on a préparé le **catalogue** à part, dans `resources/exercise-library` : 701 exercices de RepDB (une base d'exercices sous licence) et 115 propositions du kit d'Antonino. Ce travail de préparation a montré des pièges qu'aucun écran n'aurait révélés : des doublons qui ne portent pas le même nom (« Wall balls avec cible » et « Wall Ball »), des « exercices » qui sont en fait des réglages (« SkiErg 500 m » est le SkiErg avec une distance), des tags qui promettaient qu'un mouvement est « sans risque pour les genoux ». Les 701 noms et consignes ont été traduits en français. Le résultat est un **catalogue maître** reproductible : on corrige une décision, on relance le script, et les identifiants ne bougent pas. Chaque exercice a une clé lisible (`sled-pull`) et un identifiant calculé à partir d'elle, le même en développement et en production.

**La licence a guidé l'architecture.** RepDB autorise l'usage dans une application, avec une mention visible, mais interdit de republier ses données. D'où une colonne `exportable` (toujours fausse pour RepDB) et la mention affichée sur la page et sur chaque fiche. Antonino a tranché le reste : la musculation et le cardio gardent les images RepDB, la section Hyrox utilise ses propres illustrations, et la mobilité et la course sont **masquées plutôt que supprimées**. Ce sont des données, pas du code : on les réactive en changeant une ligne.

**Dans l'application**, le catalogue est une table en lecture seule (la base refuse toute modification venant de l'app), chargée par une migration générée depuis le catalogue maître. Les favoris sont propres à chaque personne, et la sécurité empêche de mettre en favori l'exercice privé d'une autre organisation. La liste (607 exercices) est filtrée directement dans la page, et les filtres restent dans l'adresse pour retrouver la liste en revenant d'une fiche. Un piège de design : les illustrations Hyrox sont détourées, avec un short et un traîneau noirs, qui disparaissaient sur le fond sombre. Elles sont donc posées sur une tuile claire, dans les deux thèmes.

### Les exercices du coach : la même table, d'autres droits (30/10)
Un coach peut maintenant ajouter ses propres exercices, avec une photo et un lien vidéo. On n'a pas créé de nouvelle table : la table des exercices avait déjà une colonne « organisation », vide pour le catalogue commun. Une ligne avec une organisation appartient à ce coach. La base l'impose de trois façons : des **droits par colonne** (l'app ne peut écrire que les champs d'un exercice du coach), des **règles par ligne** (seulement dans SON organisation, jamais le catalogue) et une **contrainte** (un exercice de coach ne porte jamais de donnée RepDB, et sa photo est rangée dans le dossier de son organisation). Les tests SQL le vérifient avec deux coachs de deux organisations.

La photo est réduite **dans le téléphone**, avant l'envoi (1 200 px au plus) : une photo de 5 Mo devient quelques centaines de Ko, et la bibliothèque reste rapide. Le serveur vérifie quand même les premiers octets du fichier, sans croire son nom. Pour la vidéo, on garde un simple lien qui s'ouvre dans l'application concernée. Intégrer Instagram ou TikTok dans la page aurait chargé leurs traceurs, et donc demandé un consentement RGPD. « Créer ma variante » reprend la rubrique, les muscles et le matériel d'un exercice du catalogue, mais pas ses consignes RepDB : l'exercice du coach reste 100 % à lui.

### La mobilité revient, et les premières consignes signées Coory (31/10)
Masquer plutôt que supprimer a payé : réafficher la mobilité a tenu en **une ligne** du fichier de périmètre, puis une nouvelle génération du catalogue. Seuls les 88 exercices RepDB qui ont une image et des consignes sont apparus ; les 20 idées du kit Coory, encore vides, restent cachées, comme les autres créations sans contenu. Les consignes et les muscles principaux des trois exercices Hyrox d'Antonino vivent dans leur propre fichier, recopiés mot pour mot, et le script refuse d'y mettre une clé qui n'est pas un exercice Coory (on ne peut pas écraser par erreur un texte RepDB) ou un muscle qu'il ne connaît pas. La migration du catalogue a été régénérée sur place, ce qui n'est acceptable que parce que rien n'est encore en ligne ; après la mise en ligne, chaque changement sera une nouvelle migration.

Pour la fiche d'un exercice, plutôt que des dessins, des **maquettes dans la vraie application** (une adresse `?maquette=1` à `5`) : mêmes composants, mêmes couleurs, mêmes données, et Antonino peut les essayer sur son téléphone avant de choisir.

### Une identité à soi : maquette d'abord, jetons ensuite (01/11)
Antonino trouvait que l'app « ressemblait à toutes les autres ». Plutôt que de retoucher l'app à l'aveugle, on a fait un **audit** puis des **maquettes HTML hors de l'app** (six versions), jusqu'à une version validée : noir, blanc et un violet rare, un nouveau logo, une seule police (Plus Jakarta Sans). La règle qui a tout guidé : la couleur de marque doit rester **rare** pour garder son sens (page active, aujourd'hui, liens), et l'action principale reste blanche ou noire. Grâce aux **jetons**, changer la palette a tenu en un fichier (`tokens.css`) : les anciens noms de variables ont été gardés, donc les pages pas encore refaites prennent déjà les nouvelles couleurs sans casser. Le tableau de bord a été refait seul, en premier, pour qu'Antonino valide dans la vraie app avant de toucher au reste. Nouveau composant : l'agenda « en cases », qui réutilise les mêmes briques d'interaction que la grille de l'Agenda (créneau vide, glisser-déposer) au lieu de les réécrire.

Le même jour, l'agenda a fait trois allers-retours, et c'est normal en design : des cases qui défilent chacune seule (trop de chiffres, les heures répétées dans chaque case), puis une **grille qui défile d'un seul bloc**, retenue sur ordinateur et téléphone. La technique la plus simple a gagné : un seul conteneur qui défile, avec des éléments « collants » (`position: sticky`) pour l'en-tête des jours, les totaux et la colonne des heures, sans JavaScript pour synchroniser quoi que ce soit. Le glisser-déposer n'a pas eu à changer : il lit la position réelle des colonnes à l'écran. Pour distinguer les jours, un jour sur deux est très légèrement gris, via un nouveau jeton de couleur réglé pour chaque thème.

Dernier morceau du tableau de bord : **changer de jour, de semaine ou de mois au doigt** sur téléphone. Pas de bibliothèque : quelques écouteurs tactiles « passifs » (ils ne bloquent jamais le défilement de la page), `touch-action: pan-y` pour laisser le défilement vertical et le zoom au navigateur, et une règle simple pour ne pas se marcher dessus avec le glisser-déposer des séances, qui bloque déjà le défilement quand une séance est attrapée : un geste bloqué n'est jamais pris pour un changement de période. En vue 3 jours, la grille défile déjà d'un jour à l'autre ; le changement de semaine ne part donc que depuis son bord. Au passage, un vieux défaut est apparu : en changeant de semaine, la grille gardait sa position de défilement. Une `key` React qui change avec la période suffit à la faire repartir proprement.

### Tester sur le vrai téléphone, puis maquetter avant de recoder (01/11)
En essayant l'app sur son iPhone, Antonino l'a trouvée peu ergonomique : trop de choses sur le tableau de bord, un agenda difficile à faire défiler. Plutôt que de recoder à tâtons, on a fait des **maquettes HTML** du tableau de bord et d'une page Agenda inspirée de Google Agenda, avec de vraies données de démo et des sélecteurs pour comparer plusieurs options (six façons de séparer deux jours, par exemple). C'est rapide à modifier, et Antonino tranche en voyant plutôt qu'en imaginant. L'étape 1 a ensuite été codée telle quelle. Un piège CSS a été instructif : pour que la page tienne exactement dans l'écran, donner `h-dvh` à la page ne suffit pas quand elle est un élément `flex-1` d'une colonne, car elle prend alors la hauteur de son contenu ; il faut aussi `flex-none`, puis une rangée de grille en `minmax(0, 1fr)` pour que les cartes se partagent l'espace restant et fassent défiler leurs listes à l'intérieur.

### Un agenda à la façon de Google, et un bug de position appris à la dure (01/11)
La page Agenda reprend l'organisation de Google Agenda : un panneau (petit calendrier, cases à cocher), une barre avec le choix de la vue au centre, et le calendrier sur toute la hauteur de l'écran. Rien n'a été réécrit de zéro : la grille, les glissés au doigt et le glisser-déposer existaient déjà, on les a déplacés et paramétrés (hauteur des heures, remplir la carte). Les raccourcis clavier (J, S, M, L) sont de simples liens ouverts par le clavier, et les cases « Individuelles / Collectives » changent l'adresse de la page : l'agenda reste partageable et le bouton « retour » du navigateur marche. Pour que la case réagisse tout de suite, elle change d'état avant même que l'agenda rechargé n'arrive.

Le bug du menu du téléphone mérite d'être retenu : un élément qui a une transformation CSS (`translate`) devient le repère de ses enfants en `position: fixed`. Le panneau ouvert gardait `translate-x-0` (un déplacement de zéro, mais un déplacement quand même), et le menu du compte, calculé par rapport à l'écran, s'affichait décalé hors du panneau. La correction tient en un mot : `translate-none` une fois ouvert.

### Le défilement « en diagonale » sur téléphone (01/11)
Sur iPhone, descendre dans l'agenda en vue 3 jours faisait aussi glisser les jours sur le côté : la grille était une seule zone qui défilait dans les deux sens, et un pouce ne descend jamais parfaitement droit. La solution vient des applications natives : **verrouiller l'axe**. La propriété CSS `touch-action: pan-y` dit au navigateur de ne gérer que le défilement vertical ; un petit script reconnaît un geste franchement horizontal (plus large que haut), fait suivre les jours au doigt, puis les pose sur une colonne. En retirant l'aimantation CSS des colonnes, un vieux défaut est apparu : pendant un glisser-déposer, la grille reculait d'elle-même dès que le doigt passait à moins de 72 px du bord, donc dans la première colonne ; l'aimantation l'annulait sans qu'on le voie. Le seuil suit maintenant la vraie largeur de la marge des heures.

### Copier ce que font les applications natives plutôt que de le simuler (01/11)
Le premier verrouillage d'axe (un script qui déplaçait les jours sous le doigt) marchait, mais il était saccadé : pas d'élan, et chaque semaine était une page à recharger. La bonne réponse était structurelle : **deux zones de défilement imbriquées**, une verticale (les heures) qui contient une horizontale (les jours), comme une rangée de vignettes dans une page. Le téléphone donne alors chaque geste à une seule zone, avec son vrai défilement natif (élan, aimantation `scroll-snap`). Seul prix à payer : l'en-tête des jours et les totaux, hors de la zone horizontale, sont recalés en JavaScript à chaque défilement. Et pour qu'on glisse librement d'une semaine à l'autre, la page envoie neuf semaines d'un coup ; sur ordinateur, une simple classe masque les jours hors de la semaine choisie. Rappel utile : le serveur de développement peut servir un CSS périmé après une modification de `globals.css` ; une variable CSS « absente » dans le navigateur, alors qu'elle est dans le fichier, se règle en le relançant.

### Un menu « sous la page », et le piège du dézoom (01/11, soir)
Antonino voulait le menu de ChatGPT : on touche ☰, la page glisse vers la droite et le menu apparaît dessous, à gauche, la page gardant un bord visible aux coins arrondis comme l'écran d'un iPhone. Une simple fenêtre par-dessus ne le permet pas : il fallait que **la page elle-même** bouge. Elle glisse avec `translate`, et ses coins s'arrondissent avec `clip-path`, découpée à la taille de l'écran (une page qui défile est bien plus haute que l'écran ; arrondir la page entière aurait mis les coins tout en haut et tout en bas du document). Deux leçons. D'abord, un élément déplacé hors de l'écran **élargit la page** aux yeux du navigateur : sur téléphone, il dézoome pour tout montrer ; `overflow-x: clip` sur le conteneur coupe ce débordement sans créer de zone de défilement (la barre du haut reste collante). Ensuite, le « + » de chaque page est rendu dans la barre du haut par un **portail React** : le bouton s'affiche ailleurs dans la page, mais garde le contexte de sa page (la fenêtre « Nouvelle séance » qu'il ouvre).

### Un popover natif et un ordre de cartes sans code en double (02/11)
L'aperçu des notifications sous la cloche utilise le **popover natif du navigateur** (l'attribut `popover` et un bouton `popovertarget`) plutôt qu'une bibliothèque : le navigateur gère seul le clic à l'extérieur, la touche Échap, le retour du focus sur la cloche et l'affichage au-dessus de tout. Son contenu ne crée aucune nouvelle règle : une fonction pure (`buildPreview`) reprend les sections déjà calculées pour la page Notifications, et une action serveur ne les lit qu'à l'ouverture, en revérifiant l'accès à l'organisation. Autre petit outil utile : pour changer l'ordre des cartes du tableau de bord **sur téléphone seulement**, les deux rangées de l'ordinateur deviennent `display: contents` (elles « s'effacent ») et chaque carte reçoit un `order` ; le même code sert les deux écrans, sans dupliquer de composant.

### La page d'une séance, mesurée au pixel près (03/11)
Antonino a fourni une maquette (ordinateur 1280 px, téléphone 390 px) avec l'exigence « 2 px d'écart au plus ». Plutôt que de comparer à l'œil, on a **mesuré** : un petit script Python lit les captures de la maquette et de la page, trouve les bords des cartes blanches et la position de chaque texte, puis compare depuis le coin de chaque carte (le menu et l'en-tête de l'app, inchangés, n'ont pas exactement les marges de la maquette). La mesure a trouvé ce que l'œil ratait : la maquette écrit ses textes avec une interligne « normale » (environ 1,26) alors que la page héritait de 1,5, soit 10 px de trop sur une seule carte ; et un bouton gardait 44 px parce que la taille du design system l'emportait sur la nôtre (deux classes de hauteur, la dernière écrite dans le CSS gagne). Ensuite Antonino a fait évoluer la page, avec trois idées réutilisables. Un en-tête qui ne change jamais d'une page à l'autre (le titre de la séance vit dans la page). Le **lien de retour monté dans la barre du téléphone**, par le même portail React que le « + » des pages (essayé, puis retiré à sa demande : la barre garde le nom de la page). Et une carte Prix « au strict nécessaire », le détail rangé dans un `<details>` natif (« Voir plus »), qui s'ouvre sans une ligne de JavaScript. Le rang « Séance 9 sur 19 » est une petite fonction pure, testée par Vitest, qui compte les dates d'origine de la série (une date déplacée garde son rang). Dernière demande : que les cartes Prochaines dates et Prix montrent **autant de lignes que l'écran le permet** (plus sur un 24 pouces que sur un MacBook). Un petit composant (`FitList`) mesure la place avec un `ResizeObserver` et cache les lignes qui dépasseraient. Le piège : en CSS, `flex: 1` a une base de 0 **%**, et un pourcentage redevient « la taille du contenu » quand la hauteur du parent n'est pas fixée ; la liste faisait alors grandir sa carte au lieu de s'y couper. Une base de 0 **px** (`flex: 1 1 0px`) règle le problème.

### Une fenêtre qui glissait sur le côté, seulement sur l'iPhone (03/11)
Dans « Nouvelle séance », Antonino pouvait faire glisser le contenu sur le côté, et le champ Heure chevauchait Durée. Deux causes qui s'additionnent. Safari impose une largeur minimale aux champs date et heure ; or une colonne de grille « 1fr » ne descend pas sous la largeur minimale de son contenu, donc le champ débordait sur son voisin. Ensuite, une fenêtre qui défile en hauteur (`overflow-y: auto`) devient aussi défilable en largeur dès que quelque chose dépasse. Corrections : des colonnes `minmax(0, 1fr)`, des champs date et heure autorisés à rétrécir, et `overflow-x: hidden` sur toutes les fenêtres. Leçon : l'ordinateur ne montrait rien (le champ heure de Chrome est plus étroit) ; c'est encore le vrai téléphone qui a révélé le bug.

### Retirer une fonctionnalité plutôt que la suivre partout (03/11)
Avant de continuer, Antonino a demandé un audit : faut-il vraiment une page Facturation ? La réponse est venue des sources officielles. En Belgique, depuis le 1er janvier 2026, une facture entre entreprises doit passer par le réseau **Peppol** (un PDF ne suffit plus), la France suit en 2026-2027 avec ses propres plateformes, et chaque pays a son système. Pour une app internationale, suivre toutes ces lois serait un métier à part entière. Décision (D-90) : Coory ne fait plus de factures ; elles se font dans le logiciel du coach (Gianluca utilise Odoo, qui sert de point d'accès Peppol). La Comptabilité devient un **aperçu visuel**, identique partout, avec une nouvelle liste « À encaisser » : les séances passées qui ont un prix et ne sont pas encore payées. Trois choix d'ingénierie à retenir. D'abord, **rien n'est effacé en base** : la migration ajoute ce qu'il faut (le taux de TVA passe sur l'organisation, repris de l'ancienne structure) et l'application cesse simplement de lire les anciennes tables ; une migration de nettoyage pourra les supprimer plus tard, une fois la décision confirmée (on appelle ça « élargir puis contracter »). Ensuite, « à encaisser » n'est **stocké nulle part** : c'est une fonction pure, testée par Vitest, qui croise les dates des séances (déplacements compris), les paiements déjà notés et les forfaits. Enfin, la cloche ne sonne qu'après une semaine sans paiement : un rappel pour chaque séance tout juste finie aurait vite noyé les vraies alertes.

### Mesurer une maquette HTML plutôt que des captures (03/11, soir)
Antonino a fourni un dossier complet pour refaire les écrans Sportifs « au pixel près » : la maquette est un fichier HTML avec tous les styles écrits en clair. Plutôt que de comparer des captures à l'œil, on a ouvert la maquette elle-même dans le navigateur et lu la position exacte de chaque élément (`getBoundingClientRect`), puis fait la même mesure sur l'app aux mêmes largeurs (1280 et 390 px, dans des cadres `iframe`). Résultat : un écart de 0 px sur les colonnes du tableau, les lignes et les cartes du téléphone. Trois leçons. La première : la maquette pouvait avoir ses propres défauts (la loupe de la recherche y était écrasée à 5 px pour faire tenir le texte) ; on ne recopie pas un défaut, on le signale. La deuxième : le cadre de l'app (menu, en-tête, marges) est commun à toutes les pages ; l'aligner sur la maquette, c'est le changer partout, d'un seul endroit, et vérifier ensuite les autres pages (tableau de bord, Agenda). La troisième : afficher deux versions d'une même ligne, l'une pour l'ordinateur, l'autre pour le téléphone, double chaque nom dans la page (les lecteurs d'écran et les tests le lisent deux fois). La ligne est donc écrite une seule fois, et c'est une grille CSS différente selon l'écran qui place ses morceaux.

### Une constante qui disparaît entre le serveur et le navigateur (03/11, soir)
En refaisant la fiche sportif, le petit point vert « Actif » ne s'affichait pas. La table des couleurs (une constante JavaScript) était déclarée dans un fichier marqué « use client », puis importée par un composant serveur. Or Next.js ne transmet pas les valeurs d'un fichier « client » au serveur : il remplace chaque export par une référence, utile pour un composant, vide pour une simple table. Leçon : ce qui est partagé entre serveur et navigateur (libellés, classes de couleur) vit dans un module neutre, sans directive ; on en a profité pour ranger les points de couleur au même endroit que les autres styles des disciplines, au lieu de quatre copies.

### Un même formulaire, deux habillages (03/11, nuit)
L'onglet Profil de la fiche reprend les champs de la page « Nouveau sportif » : mêmes libellés, mêmes limites, même validation, écrits une seule fois. La maquette leur donne pourtant un autre habillage (champs plus fins, sur-titres en capitales, grille de trois colonnes). Plutôt que de copier les champs, chaque groupe reçoit une option `look` : « app » par défaut, « fiche » sur la fiche. Les règles ne bougent pas, seul le style change, et la page « Nouveau sportif » reste telle quelle tant qu'Antonino n'a rien décidé pour elle. Deux pièges rencontrés. Pour un navigateur, un menu déroulant est toujours « en lecture seule » (`:read-only`) : le style gris prévu pour l'e-mail verrouillé grisait aussi tous les menus. Et un « ✓ » ajouté dans le texte d'une pastille changeait son nom (« ✓ Domicile ») : les tests ne la trouvaient plus. Il est maintenant dessiné en CSS (pseudo-élément `::before`), le texte reste « Domicile ».

### La semaine affichée vit dans l'adresse (03/11, nuit)
L'agenda d'un sportif avec programme montre maintenant une semaine à la fois, avec des flèches, un menu des semaines et un bouton « Toutes les semaines ». Dans la maquette, ce choix est un état du composant ; dans Coory, il est **dans l'adresse** (`?semaine=4`, `?vue=toutes`). Trois avantages : la page reste rendue par le serveur (aucune donnée en double dans le navigateur), le bouton « retour » du navigateur ramène à la semaine d'avant, et un lien partagé ou rouvert tombe sur la même semaine. Seul le petit menu des semaines est un composant « client » (il s'ouvre et se ferme), et ses choix sont de simples liens. Une semaine demandée qui n'existe pas retombe sur la semaine actuelle, comme un onglet inconnu retombe sur la vue d'ensemble.

### Un jeton qui n'existait pas encore pour le serveur (03/11, nuit)
La carte jaune de l'objectif principal restait blanche, alors que le jeton `--goal-main` était bien défini. La cause : Tailwind fabrique une classe comme `bg-goal-main` à partir des couleurs déclarées dans le thème (`@theme`), et le serveur de développement, lancé depuis plus d'un jour, n'avait pas relu ce thème. La classe n'existait donc pas, et le navigateur l'ignorait sans rien dire. Le redémarrage (cache vidé) l'a corrigé, mais a révélé une surprise : l'onglet ouvert « en verre », validé par Antonino, s'affichait lui aussi sans ses jetons (fond transparent, contour de la couleur du texte par défaut). C'est ce rendu qu'il avait aimé ; il est maintenant écrit noir sur blanc dans les jetons. Leçon : après avoir ajouté une couleur au thème, vérifier la couleur calculée dans le navigateur (`getComputedStyle`), pas seulement la classe dans le code.

### Lire une séance écrite en texte, en attendant l'éditeur (03/11, nuit)
La maquette de la page d'une séance découpe chaque ligne (« Effort · 4:55 min/km · 4 min ») et dessine le déroulé à l'échelle du temps. Or les séances actuelles sont écrites en texte libre (« 4 min @4:55 min/km »). Deux choix possibles : changer tout de suite le format des séances en base, ou lire ce texte pour l'affichage. On a choisi la lecture, dans un petit module de fonctions pures testé par Vitest, parce que le vrai format sera décidé avec l'éditeur de programmes (le cœur de Coory) et qu'il ne faut pas le figer trop tôt. Le module ne devine jamais : une ligne qu'il ne comprend pas s'affiche telle quelle, et si une seule durée manque, le déroulé n'est pas dessiné plutôt que d'être faux. Petite vérification qui rassure : la maquette annonçait « ≈ 54 min », et le calcul 20 + 5 × (4 + 1:45) + 5 donne bien 53,75 minutes.

### Deux cartes au lieu d'une grille (03/11, nuit)
L'onglet Repères montrait tous les repères en grille. La maquette n'en garde que deux, que le coach choisit (« Changer ») et qu'il peut échanger. Rien n'est perdu : le menu « Changer » liste tous les repères actuels avec leur valeur, et l'historique reste complet. Deux détails d'ingénierie. D'abord, le graphique est maintenant dessiné en pourcentages (le tracé dans un SVG étiré, les points en HTML) : il s'adapte à toutes les largeurs sans recalculer la taille du conteneur. Ensuite, les styles d'accordéon partagés entre une page serveur et un composant client vivent dans un module neutre : une constante exportée par un fichier « client » arrive vide côté serveur (leçon déjà notée plus haut). Un bug trouvé en testant à la main : choisir sur une carte le repère déjà affiché sur l'autre faisait disparaître une carte ; les deux cartes échangent maintenant leurs repères.

### Réutiliser l'option d'habillage plutôt que réécrire (04/11)
L'onglet Disponibilités a été le plus rapide de la fiche, parce que l'outil existait déjà : l'option `look` créée pour le Profil (« un même formulaire, deux habillages »). Les champs des disponibilités l'ont simplement reçue, et la page « Nouveau sportif » n'a pas bougé. La mesure a quand même trouvé un détail : chaque pastille cochée était 0,5 px plus étroite que dans la maquette, soit 2,7 px d'écart au bout de la ligne des sept jours. Le « ✓ » est dessiné en CSS et resserré pour compenser la police servie ; on était allé un peu trop loin (-1 px au lieu de -0,75 px). Le réglage profite aussi aux lieux du Profil, revérifiés dans la foulée. Leçon : un écart minuscule sur un élément répété devient visible en bout de ligne, il faut mesurer la position du dernier élément, pas seulement la taille du premier. Antonino a ensuite demandé que la carte descende jusqu'au bas du menu sur ordinateur. Pas de hauteur calculée en JavaScript : chaque niveau de la page (corps, fiche, carte, formulaire) « prend la place restante » en CSS, et c'est la zone des contraintes qui grandit. On a utilisé `flex-auto` plutôt que `flex-1` sur cette zone : avec `flex-1`, la poignée qui permet d'agrandir un texte à la main ne servait plus à rien.

### Retirer une carte sans rien effacer (04/11)
Antonino a retiré la carte « Message au sportif » : tous ses sportifs n'installeront pas l'app, le message risquait de ne jamais être lu. Retirer une carte n'est pas anodin : le même message s'affichait aussi dans la vue d'ensemble et dans l'espace du sportif. Si on ne retirait que la carte, un ancien message serait resté visible chez le sportif sans que le coach puisse le modifier ou l'effacer. On a donc retiré les trois affichages, mais rien en base : la table, la règle de sécurité (RLS) et l'action d'enregistrement restent. Revenir en arrière ne demanderait qu'à remettre l'écran. Un détail d'HTML au passage : la maquette place « Enregistrer les blessures » et « Retirer l'accord » côte à côte, alors que ce sont deux formulaires distincts. Un formulaire ne peut pas en contenir un autre ; le bouton d'enregistrement vit donc hors de son formulaire et s'y rattache par l'attribut `form`, une fonctionnalité standard du navigateur.

### Une marge de « sécurité » qui ne protégeait plus rien (04/11)
Sur téléphone, toutes les pages gardaient 120 px de vide sous la dernière carte. Cette marge datait d'une époque où l'on craignait qu'une barre du bas recouvre le contenu. Or la barre du sportif est « collée » (sticky) : elle fait partie de la page et prend sa propre place, elle ne recouvre rien. Les 120 px ne servaient plus qu'à montrer du fond gris. On les a remplacés par l'écart normal entre deux cartes (16 px). La seule page qui a vraiment un élément posé par-dessus le contenu (la barre « Écrire / Modifier » d'une séance, en position fixe) garde une marge calculée : la hauteur de la barre plus 12 px. Leçon : avant de retirer une marge, vérifier si quelque chose est réellement posé par-dessus (position fixed) ou simplement à la suite (sticky). La revue a été faite page par page au navigateur, avec un petit script qui mesure, en bas de chaque page, la distance entre la dernière carte et le bas de l'écran.

### Un bouton qui marche à moitié trahit un JavaScript absent (04/11)
Sur son iPhone, Antonino ne pouvait plus ouvrir le menu ☰, et la boîte des notifications s'ouvrait hors de l'écran. Les deux symptômes n'avaient qu'une cause : le Mac était connecté au partage de connexion de l'iPhone, une adresse (172.20.10.x) que le serveur de développement de Next n'autorisait pas. Par sécurité, Next refuse alors de servir le JavaScript de la page à cet appareil. La cloche utilise un « popover » natif du navigateur, qui s'ouvre même sans JavaScript, mais c'est le JavaScript qui le place sous la cloche : il s'ouvrait donc au mauvais endroit. Le menu, lui, dépend entièrement du JavaScript. Leçon : quand une partie de l'interface marche et l'autre non, se demander d'abord si le JavaScript s'exécute ; le journal du serveur le disait en toutes lettres (« Blocked cross-origin request »). Au passage, le serveur de développement s'était mis à recharger les pages en boucle ; un redémarrage à neuf (cache vidé) l'a réglé. Pour le vérifier sans téléphone, un petit script Playwright émule l'iPhone 17 Pro Max et compte les rechargements.

### Faire le ménage avec un outil, pas à l'œil (04/11)
Après la fiche sportif, Antonino a demandé de nettoyer le dossier : code mort, maquettes, fichiers devenus inutiles. Pour le code, pas de recherche au hasard : un petit script utilise le compilateur TypeScript du projet. Il part des points d'entrée (les pages et layouts de Next, les tests, les scripts), suit tous les imports, et demande pour chaque export « qui l'utilise ? ». Résultat : l'app était déjà assez propre (un seul fichier jamais importé), mais il restait des fonctions qui ne servaient plus qu'à leurs propres tests, vestiges d'anciennes versions de l'agenda. Un test qui protège une fonction morte donne une fausse impression de couverture : on a retiré les deux ensemble. Pour les fichiers, la règle a été simple : on garde ce qui sert à avancer (le code, les specs métier, la chaîne du catalogue d'exercices, le bon design system), on retire ce qui est déjà réalisé ou remplacé. Rien n'est vraiment perdu : tout était commité, Git garde chaque fichier supprimé.

### Le logo définitif, sans le redessiner (04/11)
Antonino a fourni un kit complet pour son logo : les tracés exacts, les couleurs, les proportions, les icônes de toutes tailles et un composant React. La règle du kit est stricte : ne jamais redessiner. L'app ayant un thème clair et un thème sombre, le composant officiel est affiché dans ses deux tons et la feuille de style ne montre que le bon, plutôt que de modifier ses couleurs. Deux pièges évités. Next.js ajoute tout seul les icônes posées dans `src/app/` (favicon.ico, icon.svg, apple-icon.png) : laissées en place, elles seraient passées devant les nouvelles. Et l'adresse du site (`metadataBase`) sert à écrire l'adresse complète de l'image de partage : tant que le domaine n'est pas choisi, elle reste en commentaire. Dans la foulée, la sidebar a été réglée : les onglets descendaient de 7 px quand on la repliait, parce que le bouton « Déplier » était plus haut que le logo. ### Une coque commune avant 36 boîtes (04/11)
Antonino a fourni un kit qui redessine les 36 boîtes de l'app (menus, formulaires, confirmations, grands panneaux). Plutôt que de les reprendre une à une, on commence par ce qu'elles partagent : quatre composants (la coque, l'en-tête, le pied, les champs) couvrent 34 boîtes sur 36. Les couleurs du kit sont devenues des jetons (`--dlg-*`) avec leur version sombre, pour qu'aucune boîte n'écrive une couleur en dur. Le changement le plus important ne se voit pas : avant, toute la fenêtre défilait ; maintenant, seul le corps défile, l'en-tête et le pied restent en place, comme dans une app native. Deux pièges évités. La sortie animée joue sur une copie de la fenêtre : il a fallu lui recopier la position du corps qui défile, sinon le contenu sautait en haut pendant la fermeture. Et deux écrans comptaient sur l'ancien défilement (le retour en haut des Paramètres, le bouton collé en bas de « Nouvelle séance ») : repérés par une recherche avant de livrer, pas après.

### Mesurer contre la maquette plutôt qu'à l'œil (04/11)
Pour les six premiers menus, un script ouvre la même boîte dans l'app et dans la maquette du kit, puis relève la position de chaque texte, tuile, icône et filet par rapport au coin de la boîte. Les deux listes se comparent ligne à ligne : tout écart saute aux yeux. Il a trouvé un décalage de 1 px que l'œil n'aurait jamais vu : la description sous une action avait l'interligne par défaut au lieu de 1,4. Il a aussi évité une fausse piste : l'anneau de focus semblait noir au lieu de violet, mais il était juste en train de changer de couleur (une transition de 150 ms sur toutes les couleurs, contour compris). En limitant la transition au fond, l'anneau apparaît violet tout de suite. Leçon : un écart mesuré au mauvais moment peut être une animation, pas un défaut.

### Une icône ne traverse pas la frontière serveur / client (04/11)
Chaque confirmation du kit a son icône : un bouclier pour retirer un accord, une porte de sortie pour « Déconnecter partout ». Le plus simple aurait été de passer l'icône elle-même au bouton de confirmation. Mais ce bouton est un composant client (il gère l'ouverture de la fenêtre), et les pages qui l'utilisent sont rendues sur le serveur : Next.js ne peut envoyer au navigateur que des données (textes, nombres, objets simples), jamais une fonction, et une icône Lucide est une fonction. La solution : passer un nom (« shield », « logout ») que le bouton traduit lui-même en icône. Au passage, la phase a révélé un vrai défaut de texte : la gestion des catégories, commune aux documents et aux dépenses, disait « ses documents restent » même quand on supprimait une catégorie de dépenses. Le kit l'avait corrigé dans sa maquette, sans savoir que le composant servait aux deux.

### Deux icônes que Lucide n'a pas (04/11)
Le kit dessine le Running par une silhouette qui court et l'Hybride par deux cercles qui se croisent ; Lucide, la bibliothèque d'icônes de l'app, n'a ni l'un ni l'autre. Plutôt que d'insérer des images, on fabrique de vraies icônes Lucide avec sa propre fonction `createLucideIcon` et les tracés du kit : elles prennent la même taille, la même épaisseur de trait et la même couleur que les autres, et s'utilisent exactement pareil. Au passage, l'ancien fichier d'icônes de discipline ne servait plus que dans ces menus : une fois remplacé, il est devenu du code mort, retiré aussitôt. Enfin, la mesure a montré une différence qui n'en était pas une : le kit écrit la couleur d'un chevron dans le tracé, l'app dans la couleur du texte ; à l'écran, c'est le même gris.

### Un bouton d'envoi hors de son formulaire (04/11)
Dans le kit, le bouton « Enregistrer » d'un formulaire est dans le pied de la fenêtre, qui reste en place pendant que les champs défilent. Le formulaire, lui, est dans la zone qui défile : le bouton n'est donc plus à l'intérieur. HTML prévoit ce cas : l'attribut `form="id-du-formulaire"` relie un bouton à un formulaire où qu'il soit. Rien ne change pour la logique : même envoi, mêmes validations, mêmes messages. Deux leçons de mesure. Une classe de bouton qui portait deux tailles de texte (15 et 14,5 px) laissait le navigateur choisir selon l'ordre de la feuille de style : on ne met plus qu'une taille par classe. Et la maquette, qui charge sa police sur Internet, s'est un jour affichée avec une police de secours : ses pastilles devenaient plus étroites, et la comparaison criait à l'écart. Le script vérifie maintenant que la police est chargée avant de mesurer.

### Quand la maquette se trompe (04/11)
Comparer l'app à la maquette élément par élément a un effet inattendu : on trouve aussi les erreurs de la maquette. Dans « Nouveau paiement », la carte « Forfait sur une période » est écrasée dans une seule colonne sur ordinateur (un texte de 55 px de large et 250 px de haut) : sur le téléphone de la même maquette, elle prend toute la largeur. Ailleurs, deux cartes à cocher affichent « 6 » en guise de description. On ne recopie pas une erreur au pixel près : on suit l'intention (la version téléphone, une vraie description) et on le signale. Autre leçon de la phase F : un test qui cherchait « Montant reçu (TVAC… » a cassé quand le libellé du kit est devenu « Montant reçu », avec « € TVAC » dessiné dans le champ. Plutôt que de modifier le test, le libellé lu par les lecteurs d'écran garde « (TVAC, EUR) » : l'information n'était plus dite qu'aux yeux, elle l'est de nouveau à l'oreille.

### Un menu collé à son bouton (04/11)
Deux menus du kit ne s'ouvrent pas au centre de l'écran : le choix de la vue de l'agenda descend sous son bouton, le menu du compte remonte depuis la carte du coach, en bas à gauche. Plutôt qu'un composant de plus, la coque commune a reçu une option « ancre » : sur ordinateur, la position et la largeur viennent du bouton (mesuré au moment du clic) ; sur téléphone, rien ne change, c'est une feuille du bas. Même l'animation suit : le menu grandit depuis le côté de son bouton, pas depuis son centre. Un choix assumé : le menu du compte s'ouvrait aussi au survol de la souris ; avec le voile sombre du kit derrière lui, un simple passage du curseur aurait assombri tout l'écran. Il s'ouvre donc au clic.

### Un seul « Enregistrer » pour deux formulaires (04/11)
Dans le kit, la section Profil des Paramètres réunit le prénom, le nom, l'entreprise, le téléphone et le nom de l'organisation sous un seul bouton « Enregistrer ». Dans le code, ce sont deux enregistrements différents : le profil du coach, et le nom de l'organisation que seul le propriétaire peut changer. Les fusionner aurait changé la logique. HTML permet de les garder séparés tout en les affichant ensemble : deux formulaires vides, invisibles, et chaque champ relié au sien par l'attribut `form`. Le bouton du pied envoie le profil, puis le nom de l'organisation s'il a changé. La mesure a d'ailleurs trouvé un piège amusant : ces deux formulaires vides comptaient comme deux éléments de la colonne, et l'espace de 22 px entre éléments s'ajoutait deux fois. Les rendre invisibles (attribut `hidden`) a tout remis en place, au pixel près.

### Un nouveau kit, et la méthode d'abord (04/11)
Antonino a fourni un kit de 13 pages. Avant de toucher au code, on a fait l'audit demandé par le kit : pour chaque fonctionnalité dessinée, ce qui existe déjà dans l'app, ce qui change seulement d'apparence, et ce qui est vraiment nouveau. Résultat : beaucoup de « nouveautés » existaient déjà (période de la comptabilité, inscrits d'une séance, accord pour les blessures…). Les vraies questions (données à créer, choix de design contradictoires dans le kit) ont été posées une fois, ensemble, et les réponses écrites dans le kit et en mémoire. La page « Inviter » a servi de première page : ses briques (pastille d'état, barre d'actions fixe du téléphone, fil d'Ariane) sont des composants partagés que les pages suivantes réutiliseront, au lieu d'être recopiés. Un piège rencontré : le fichier qui fixe la durée d'un lien (7 jours) est réservé au serveur, parce qu'il fabrique aussi les jetons secrets ; la page lui passe donc la valeur, le navigateur n'importe jamais ce fichier.

### Des tests qui échouaient au hasard : deux tests sur le même créneau (05/11)
Quatre tests échouaient de temps en temps, puis réussissaient quand on les relançait seuls. Plutôt que d'augmenter les délais au hasard, on a relancé ces tests en boucle en gardant leurs « traces » (l'enregistrement de chaque action). La première trace a donné la réponse : pendant 29 secondes, le test cliquait sur un créneau vide de l'agenda, et une séance d'un AUTRE test, qui tournait au même moment, était posée dessus. Ce test-là créait une série « chaque mercredi à 10:00 » sans date de fin, qui tombait sur les créneaux des voisins. On l'a déplacée à 08:00. Le reste venait vraiment de la charge : tout tourne sur le même Mac, et les délais par défaut étaient trop courts ; ils sont passés de 30 à 60 secondes par test. Enfin, ces vérifications ont trouvé une vraie fragilité dans l'app : l'ancienne adresse des Paramètres faisait sa redirection en cours de page, et pouvait laisser une page blanche quand le serveur était chargé. La redirection est maintenant faite avant même que la page commence.

### Assez de démonstration pour voir « Voir plus » (05/11)
La page Documents montre 7 lignes, puis « Voir plus » ; avec 4 documents de démonstration, ce bouton n'apparaissait jamais, donc on ne pouvait pas le juger. ### La validation finale du kit : mesurer plutôt que regarder (05/11)
Le kit se termine par une « validation globale » : toutes les pages, de 320 à 3 440 pixels de large, au clavier, en accessibilité, sans rien casser. Plutôt que d'ouvrir 13 pages à 9 largeurs à la main, un script a fait le travail : il ouvre chaque écran, cherche ce qui dépasse de l'écran, les boutons sans nom pour un lecteur d'écran, les textes trop pâles pour leur fond, et appuie 45 fois sur Tab pour suivre le focus. Sa leçon principale vient de ses erreurs : la première mesure des zones tactiles se trompait, car elle ne voyait pas qu'une ligne entière de notification est cliquable (un lien « étiré » sur toute la ligne). La bonne mesure imite un doigt : elle demande au navigateur, point par point autour d'un bouton, ce qui serait touché. Il restait quatre vraies petites cibles ; elles ont été agrandies sans changer un pixel à l'écran (une marge invisible qui réagit au toucher), et des captures avant / après l'ont prouvé. La validation a aussi trouvé un trou dans les tests : la table des listes de tâches n'avait pas son test d'isolation entre coachs. Il est écrit. Ce qui ne se vérifie que sur un vrai iPhone (le clavier ouvert, l'encoche) est noté pour la séance iPhone.

### Corriger sans redessiner (05/11)
Antonino a dit oui aux quatre propositions de la validation. Deux idées les guident. D'abord, ne pas toucher aux couleurs des disciplines, utilisées partout (agenda, programmes) : on a ajouté à côté des variantes « texte », un peu plus claires en sombre et plus foncées en clair, réservées aux petits textes posés sur un fond pâle ; le design system grandit d'un cran au lieu de changer. Ensuite, agrandir la zone qu'on touche sans agrandir ce qu'on voit : une règle partagée (`tap-44`) ajoute, seulement sur les écrans tactiles, un calque invisible qui prolonge chaque pastille jusqu'à 44 pixels de haut. La preuve que rien n'a bougé à l'écran vient des captures : avant et après sont identiques au pixel près, sauf les couleurs qu'on voulait changer. Enfin, sur très grand écran, la liste des tâches et le fil des messages ne s'étirent plus sur trois mètres : la carte des tâches s'arrête à 1 370 pixels et le fil se centre sur 860, comme le proposait le kit.

### Le bug qui n'existait que sur le vrai iPhone (05/11)
Sur l'iPhone d'Antonino, plusieurs boîtes ne s'affichaient pas : l'écran s'assombrissait, puis rien. Dans Chrome, en vue téléphone, tout marchait : impossible de reproduire. Plutôt que de deviner, on a interrogé le téléphone lui-même : pendant quelques minutes, le serveur de développement a affiché, une seconde après chaque ouverture, une alerte avec la taille et la position de la boîte. Réponse : la boîte était bien ouverte, mais haute de 0 pixel. La cause tient en un mot de CSS : les parties de la boîte étaient réglées en `flex-1`, ce qui veut dire « pars de 0 et prends la place qui reste ». Quand la boîte n'a pas de hauteur fixe, il n'y a pas de place qui reste : Chrome mesure quand même le contenu, Safari prend le 0 au pied de la lettre. En `flex-auto` (« pars de la taille de ton contenu »), les deux navigateurs sont d'accord. Leçon : un émulateur de téléphone dans Chrome reste Chrome ; seul le vrai appareil dit la vérité, et un petit diagnostic bien placé vaut mieux que dix hypothèses.

Dans la foulée, deux réglages vérifiés directement sur l'iPhone. `viewport-fit=cover` : le code prévoyait déjà des marges pour l'encoche et la barre d'accueil, mais ces marges valaient 0 tant que la page ne demandait pas à aller jusqu'aux bords. Et la conversation des Messages occupe maintenant tout l'écran du téléphone : la page fait exactement la hauteur de l'écran (comme l'Agenda), ce sont les messages qui défilent dans la carte, et la saisie reste en bas ; quand le clavier apparaît, iOS remonte la page pour garder la saisie visible.

### Un assistant qui dit qu'il n'est pas encore branché (05/11)
Tout le design de l'Assistant IA est en place : la boîte qui s'ouvre par-dessus n'importe quelle page, la page complète avec son historique, le choix du sportif concerné, les raccourcis. Chaque demande reçoit donc la même réponse, honnête : l'assistant n'est pas encore branché, rien n'a été envoyé. Rien n'est enregistré non plus, et l'historique le dit au lieu d'inventer des conversations. Quand le fournisseur sera choisi, il suffira de remplacer cette réponse par la vraie ; la carte « Actions proposées », avec ses cases à cocher, attend déjà.

### Des Messages comme une messagerie (05/11)
La page Messages a pris l'allure d'une vraie messagerie : la liste et le fil côte à côte à la hauteur de l'écran, une recherche, un bouton « Nouveau message » qui demande à qui écrire, et les messages rangés par jour. La Comptabilité gardait ses calculs, mais pas sa mise en page : d'abord le résultat de la période choisie, en grand, puis le graphique et la répartition, puis les mouvements, et enfin le tableau, replié tant qu'on ne le demande pas. ### Des listes à soi, et une tâche en une ligne (05/11)
Les tâches avaient cinq catégories fixes (programme, facturation…), décidées par l'app. Antonino a choisi que chaque coach crée ses propres listes, nommées et colorées comme il veut, et qu'un coach qui arrive n'en ait aucune. ### Masquer n'est pas supprimer (05/11)
Les notifications de Coory ne sont stockées nulle part : elles sont calculées à partir des vraies données (un message non lu, une séance pas payée). On ne peut donc pas « supprimer » une notification comme un e-mail. Ce que la base garde, c'est le choix du coach pour chacune : lue, masquée, et maintenant supprimée. Masquer la range dans un onglet « Masquées », d'où elle peut revenir ; supprimer la cache partout, pour de bon. Chaque action propose « Annuler » pendant 5 secondes, ce qui revient simplement à effacer la date posée. Un piège trouvé par un test qui échouait une fois sur cinq : ouvrir une notification la marquait lue en même temps que la page changeait, et le recalcul déclenché par l'enregistrement pouvait annuler le changement de page. Maintenant on enregistre d'abord, puis on y va.

### Des Paramètres sans page, et un seul bouton par rubrique (05/11)
Les Paramètres n'ont plus d'adresse à eux : ils s'ouvrent toujours en fenêtre, par-dessus la page où l'on est. Un ancien lien (favori, e-mail) vers la page des Paramètres mène au tableau de bord, la fenêtre ouverte à la bonne rubrique ; l'adresse est ensuite nettoyée, pour qu'un retour arrière ne la rouvre pas. Sur téléphone, la fenêtre prend tout l'écran et un menu déroulant remplace le sommaire. Chaque rubrique n'a plus qu'un bouton « Enregistrer », alors que derrière il y a parfois plusieurs enregistrements (les valeurs par défaut et les interrupteurs de la cloche ; le pays et la TVA). La technique déjà utilisée pour le Profil a servi : des formulaires invisibles, chaque champ relié au sien, et le bouton les envoie l'un après l'autre. Un détail corrigé en passant : l'aide du prix disait toujours « la TVA de 21 % s'ajoute » ; elle lit maintenant le taux réglé par le coach.

### Un formulaire long qui se lit en six étapes (05/11)
« Nouveau sportif » (page 10 du kit) garde tous ses champs, mais en six cartes numérotées qu'on lit de haut en bas, et le bouton « Enregistrer le sportif » reste grisé tant que le prénom est vide : c'est le seul champ obligatoire, la vérification du serveur reste la même. ### Un verrou qui doit vivre là où on ne peut pas le contourner (06/11)
Coory reste une bêta privée : l'app est visible de tous, mais seuls les testeurs à qui Antonino donne un code peuvent créer un compte. Le premier réflexe aurait été de vérifier le code dans notre formulaire. Or la « clé publique » de Supabase est, par définition, dans le navigateur de chaque visiteur : n'importe qui peut appeler l'inscription directement, sans passer par notre page. Le contrôle vit donc DANS Supabase : un « crochet » (une fonction SQL que Supabase appelle avant de créer chaque compte) accepte ou refuse. On l'a vérifié en se mettant à la place de l'attaquant : un appel direct sans code, puis avec un faux code, est refusé (403) ; avec le bon, le compte est créé. Trois détails comptent : le code est rangé haché (comme un mot de passe), il est retiré des données du compte après la création (Supabase réécrit ces données juste après, il a fallu le retirer aussi à la mise à jour), et sans code enregistré les inscriptions sont fermées : une erreur de configuration ferme la porte au lieu de l'ouvrir. Les sportifs invités par leur coach, eux, sont créés par le serveur et passent sans code.

### Une page d'erreur qui ne doit dépendre de rien (06/11)
Les pages « Page introuvable » et « Une erreur est survenue » ont été redessinées par Antonino, dans le cadre de l'app (menu et en-tête). Next.js permet de poser ces pages à plusieurs niveaux : dans l'espace coach, elles s'affichent à l'intérieur de la coquille ; à la racine, elles servent de filet quand la coquille elle-même a planté ou quand le visiteur n'est pas connecté. La page d'erreur ne fait aucun appel réseau : si l'app est en panne, elle doit quand même s'afficher. Elle ne montre jamais le détail technique de l'erreur (qui peut contenir des informations sensibles), seulement une courte référence tirée de l'identifiant que Next donne à chaque erreur du serveur, pour la retrouver dans les journaux.

### Changer la couleur de 1 200 images sans les redessiner (06/11)
La nouvelle maquette de la Bibliothèque remplace le ciel bleu des illustrations par une lavande, plus proche du violet de Coory. Mais la maquette ne fournissait que 20 images, et l'app en a près de 1 200 venues de RepDB. Deux pièges : la licence de RepDB permet de recolorer ses images, mais interdit de les donner à une IA qui les redessinerait ; et une couleur « à peu près » se verrait d'une carte à l'autre. La solution est un petit script sans IA : il trouve la couleur du ciel (la plus fréquente de l'image), la décale vers la lavande, adoucit les bords, et ne touche qu'au ciel RELIÉ au fond, comme un pot de peinture, pour ne pas teinter les reflets bleutés des baskets. Avant de l'appliquer partout, on l'a mesuré sur les images de la maquette : moins de 1,6 point d'écart moyen sur 255, invisible. Les originaux restent dans un cache hors de Git, ce qui permet de refaire l'opération si la couleur change un jour.

### Reproduire une maquette sans casser le design system (06/11)
Antonino a dessiné ses pages de connexion, d'inscription, de bienvenue et légales, avec un dossier de transmission très précis (styles exacts, images, captures). La consigne était double : au pixel près, ET cohérent avec le reste de l'app. La bonne surprise : les couleurs de la maquette existaient déjà presque toutes dans la famille de jetons des fenêtres de l'app ; quand l'écart était invisible (un gris à 1 % près), on a gardé le jeton de l'app, et seules les vraies nouveautés (fond lavande, bloc « provisoire », voile sur la photo) sont devenues de nouveaux jetons, avec leur version sombre. Pour comparer, chaque page est capturée aux tailles exactes de la maquette (1 200 × 760 et 390 × 844), puis les positions sont mesurées ligne par ligne : on a corrigé jusqu'à un pixel d'écart. Le dossier se contredisait parfois (deux tailles de titre) : on suit le fichier source, classé « exact », et on le signale. Enfin, une fonctionnalité dessinée doit marcher : « Se souvenir de moi » n'existait pas, elle fonctionne maintenant (case décochée, la session disparaît à la fermeture du navigateur).

### Les briques avant les écrans, mesurées dans le code des maquettes (09/11)
Avant de construire les écrans Programmes, on a posé leurs briques communes : segmenté, menu déroulant, pastilles, interrupteur, choix, menu « ··· » et carte de séance. Plutôt que de mesurer les captures à l'œil, un agent a relevé les valeurs exactes dans le code source des maquettes (hauteurs, rayons, couleurs, ombres, états). Deux principes ont guidé le travail. D'abord, réutiliser ce qui existe et a été validé (la feuille du bas qui se glisse au doigt, le bouton « + »), et signaler les écarts plutôt que de dupliquer un composant presque identique. Ensuite, n'ajouter un jeton de couleur que s'il manque vraiment : quatre valeurs seulement (un anneau et trois ombres), le reste existait déjà. Les commandes sont des éléments natifs (boutons radio, case au rôle « interrupteur », menu `<select>`), ce qui donne gratuitement le clavier, les lecteurs d'écran et, sur téléphone, le sélecteur du système. Incident : le serveur de développement ne générait pas les nouvelles classes ; une construction neuve prouvait que le code était bon, et un redémarrage a suffi. Leçon : quand un style « n'existe pas », on vérifie d'abord avec une compilation propre avant de toucher au code.

Ensuite, les écrans eux-mêmes : la page Programmes, l'assistant de création, l'éditeur d'un programme et l'éditeur d'une séance Running. Le choix central : un programme en cours d'écriture est **un seul document** (le brouillon), enregistré tout seul 700 ms après la dernière modification, avec un numéro de révision. Si le même programme a été modifié ailleurs entre-temps, le serveur refuse au lieu d'écraser et l'écran l'annonce ; c'est le « verrou optimiste », plus simple qu'un verrou classique et suffisant pour un coach seul. Toutes les opérations (déplacer une séance, dupliquer une semaine, ajouter un bloc « Répéter ») sont des fonctions pures testées à part, l'interface ne fait que les appeler. Sur téléphone, l'éditeur devient une pile de trois écrans (semaines, une semaine, une séance) avec le retour dans la barre du haut. Le glisser-déposer des étapes est écrit à la main (Pointer Events) plutôt qu'avec une bibliothèque : une courte liste verticale ne le justifiait pas, et le clavier (flèches) marche aussi. Incident utile : la construction de production a échoué alors que le serveur de développement fonctionnait, parce qu'une page générique n'avait plus rien à pré-générer. Leçon : lancer régulièrement le vrai build (les tests Playwright le font), le mode développement est plus tolérant.

Pour finir la phase, les jours fixes, l'onglet Programme du sportif, l'agenda déplié et la publication. Un test de bout en bout (créer depuis la fiche, fixer les jours, publier) a trouvé un vrai défaut que les essais à la main n'avaient pas vu : en publiant juste après une modification, l'éditeur enregistrait bien, mais envoyait au serveur l'ancien numéro de révision, lu dans l'état de l'écran qui n'était pas encore rafraîchi ; le serveur, prudent, refusait. La correction lit le numéro au moment même de l'envoi. Leçon : une valeur d'état React lue juste après une action asynchrone peut être en retard d'un rendu ; pour ce qui part au serveur, on lit la référence à jour. Autre choix assumé : l'onglet Programme ne marque aucune séance « faite » tant que le sportif ne peut pas l'envoyer (son espace viendra plus tard), plutôt que d'afficher des données inventées. Juste après, Antonino a trouvé en testant qu'une deuxième séance ne s'ajoutait pas. La cause : Next.js 16 garde les pages déjà visitées « en coulisse », avec leur état React ; en revenant d'une séance, l'éditeur du programme réapparaissait avec l'ancien brouillon et un vieux numéro de révision, que le serveur refusait à juste titre. La correction donne à l'éditeur une « clé » égale à la révision lue sur le serveur : si le brouillon a changé, React repart de zéro avec les bonnes données. Leçon : avec ce cache de pages, un état initialisé depuis des props ne suit pas les nouvelles props ; il faut une clé, ou le relire.

### Les programmes deviennent modifiables : un brouillon, des versions figées (09/11)
Jusqu'ici, un programme ne se lisait qu'à partir d'une version publiée et figée, posée par le seed. Avant de dessiner l'éditeur, il fallait décider comment stocker ce que le coach modifie. Deux voies : découper le programme en tables (semaines, séances, blocs), comme le proposait la maquette, ou garder **un brouillon par programme**, un seul document JSON validé par Zod, comme le prévoyait le cahier des charges. La seconde a gagné : elle colle aux versions figées déjà en place (publier = copier le brouillon dans une nouvelle version) et elle rend la copie d'un modèle triviale. Le risque d'un gros document, c'est d'écraser le travail d'un autre onglet : chaque enregistrement porte un **numéro de révision**, et la base refuse une révision périmée au lieu d'écraser. Le contenu d'une séance est maintenant **structuré par discipline** (étapes et allures pour le Running, séries et % du max pour la musculation, blocs et stations pour l'Hyrox), et l'ancien format en texte reste lisible : les anciennes versions ne sont jamais réécrites, et le seed garde ses 600 séances en texte justement pour le prouver. Trois règles métier sont passées dans la base plutôt que dans le code : deux programmes publiés d'un sportif ne se chevauchent jamais (une **contrainte d'exclusion** sur les périodes), une version publiée ne s'écrit que par une fonction contrôlée, et un modèle Coory ne se modifie pas. Les charges officielles Hyrox ont été recopiées depuis le règlement officiel de la saison, pas depuis des sites qui se contredisaient. Leçon : on décide du stockage avant de dessiner l'écran, et chaque règle qui ne doit jamais être contournée va le plus bas possible, dans la base. Un test de parcours a aussi révélé un vieux défaut que les nouvelles données ont rendu visible : la carte « Programmes en cours » départageait au hasard des programmes qui commencent le même jour ; un tri sans départage n'est jamais stable, on ajoute toujours une clé de plus (date de création, puis identifiant). Vérifié par 503 tests SQL, 332 tests unitaires, toute la suite de parcours et un essai complet contre la base locale.

### Retirer un graphique, et tout ce qui ne servait qu'à lui (08/11)
La page d'une séance montrait sous les étapes un « déroulé » en barres, repris de la maquette. Antonino l'a jugé décoratif : les étapes disent déjà tout. Retirer l'affichage ne suffisait pas : le calcul des durées de chaque ligne, une fonction de durée par étape et un jeton de couleur n'existaient que pour ce graphique. Les laisser aurait créé du code mort, testé mais inutile. On a donc suivi chaque fonction jusqu'à ses usages, retiré ce qui ne servait qu'au graphique, et gardé ce que la page utilise encore (le découpage « Effort · 4:55 min/km · 4 min »). Leçon : une suppression se fait jusqu'à la racine, et la règle est notée dans le brief des futures maquettes pour ne pas la voir revenir.

### Nettoyer sans effacer ce qui sert encore (07/11)
Un dossier propre ne veut pas dire un dossier réduit au code visible. L'audit a suivi les imports de tous les fichiers TypeScript depuis les routes Next.js, vérifié les exports, les dépendances, les images publiques, les documents et leurs liens. Un seul ancien composant n'était plus accessible. Les builds, rapports et caches ont été retirés parce qu'ils se recréent, tandis que les spécifications, la prochaine maquette Programme, les sources du logo, le catalogue d'exercices et les moteurs prévus ont été gardés parce qu'ils servent encore à construire ou reproduire l'app. La leçon est simple : on supprime à partir de preuves, pas seulement parce qu'un fichier n'apparaît pas dans une page aujourd'hui. Le résultat a été vérifié par lint, TypeScript, formatage, 271 tests unitaires et un build de production de 63 pages.

### Le titre qui disparaissait : une page cachée n'est pas une page partie (05/11)
Sur téléphone, le nom de la page en haut ne s'affichait parfois plus, jusqu'au rechargement. Cause : pour revenir vite en arrière, Next garde la page quittée dans la page, simplement cachée. Ce qu'elle avait posé dans la barre (son bouton retour, le mois de l'Agenda) y restait aussi, invisible, et la règle qui masque le nom « quand la barre contient quelque chose » le voyait encore. La correction compte les pages qui posent quelque chose dans la barre EN CE MOMENT : une page cachée arrête ses effets, elle ne compte plus. Un test reproduit le parcours (Agenda, puis Sportifs, puis une fiche, puis le tableau de bord) ; on a vérifié qu'il échoue sans la correction avant de la garder.

### Une règle d'en-tête plutôt qu'une maquette (05/11)
Le kit dessinait, pour les pages « à l'intérieur » d'une autre, un petit fil d'Ariane au-dessus du titre : la barre d'en-tête grandissait et ressemblait à un titre avec sous-titre. Antonino a tranché : une seule ligne, « ← Bibliothèque · Créer un exercice », la barre garde partout la même hauteur, et sur téléphone le titre respire sous la barre. Comme toutes les pages passent par le même composant d'en-tête, la règle s'applique en un seul endroit à tout le site, et elle est écrite dans les instructions du projet pour les pages à venir, même si une maquette dit l'inverse. Deux détails ont demandé de mesurer plutôt que de deviner : la limite du lien de retour se calcule sur la largeur réelle de la ligne (unité « cqi » d'une requête de conteneur), et les pastilles d'une fiche exercice ne s'affichent que s'il reste la place ; à 1 024 px, la recherche se replie en loupe sur les pages qui ont aussi des boutons, sinon le chemin devenait illisible.

### Une page qui calcule pendant qu'on tape, et un écran trop étroit (04/11)
« Modifier la séance » (pages 06 et 12 du kit) montre en haut un récapitulatif qui suit la saisie : le jour et l'heure (« Chaque jeudi, 07:00 »), la durée, la fin, le prix payé par le sportif et le mode de paiement, et, pour une séance collective, le prix par inscrit. Ce calcul n'est qu'un affichage : rien de nouveau n'est enregistré, la facturation reste celle d'avant. Le taux de TVA vient des Paramètres de l'organisation, jamais d'un 21 % écrit dans le code : à 0 %, la page le dit (« sans TVA »). La recherche parmi les sportifs inscrits masque des cases sans les retirer du formulaire, sinon chercher un nom aurait désinscrit les autres. Enfin, la vérification à toutes les largeurs a servi : à 1 024 px, les cinq colonnes du récapitulatif se chevauchaient ; elles passent sur leur propre ligne jusqu'à 1 279 px, comme le prévoyait le kit.

### Une page presque gratuite (04/11)
La page « Créer un exercice » (page 08 du kit) avait déjà pris son nouveau visage avec la page 11, puisque les deux partagent le même formulaire : il ne restait que ce qui est propre à la variante (le bandeau qui rappelle l'exercice d'origine et le lien pour le revoir, le bouton « Enregistrer ma variante ») et le bouton flottant de la Bibliothèque sur téléphone. C'est l'intérêt d'un composant partagé : une amélioration profite à toutes les pages qui l'utilisent, et une page de plus coûte peu. La maquette n'avait ni photo ni lien vidéo à la création ; on les a gardés, parce qu'une fonctionnalité qui existe ne disparaît pas à cause d'un dessin incomplet.

### Un aperçu qui suit la saisie (04/11)
La page « Modifier l'exercice » (page 11 du kit) montre en haut un aperçu de l'exercice qui change pendant qu'on tape : nom, rubrique, muscles, matériel. Pour cela, ces quatre champs sont maintenant « contrôlés » : leur valeur vit dans l'état de la page, et le formulaire comme l'aperçu la lisent. Les autres champs (consignes, lien vidéo, photo) restent libres, le navigateur les envoie tels quels : aucune action serveur n'a changé. Les boutons Enregistrer sont hors du formulaire (dans l'aperçu sur ordinateur, dans la barre fixe sur téléphone) : l'attribut HTML `form` les y relie. Deux leçons : le formulaire est partagé avec « Créer un exercice », donc les deux pages changent ensemble (un seul code à tenir) ; et le serveur de développement peut servir une ancienne version d'un fichier modifié (ici, le style du bouton « Annuler » arrivait vide) : on le relance et on revérifie avant d'annoncer que c'est fini.

### Un tableau sur ordinateur, une liste sur téléphone, une seule page (04/11)
La page Documents (page 05 du kit) montre un vrai tableau sur ordinateur et une liste de lignes sur téléphone. Plutôt que d'écrire deux pages, chaque document est UNE ligne dont les cellules s'affichent ou se cachent selon la largeur : le même code, les mêmes boutons, les mêmes tests. Pour qu'un lecteur d'écran comprenne le tableau, les lignes portent les rôles d'un tableau (en-têtes, cellules, sens du tri annoncé). Toute la ligne s'ouvre au toucher grâce à une astuce simple : le bouton du nom s'étend, invisible, sur toute la ligne, et seuls le sportif et « ••• » passent au-dessus. Le tri et « Voir plus » se font dans le navigateur, sur les documents déjà chargés : aucune nouvelle requête. Le tri des colonnes devient une brique partagée, que la Comptabilité réutilisera. Pour vérifier « Voir plus » et le tri, il fallait plus de documents que la démo n'en a : dix documents fictifs ont été ajoutés le temps des captures, en base locale seulement, puis effacés par la remise à zéro.

### La TVA n'était pas obligatoire, mais tout le laissait croire (04/11)
Antonino a demandé pourquoi on était « obligé » de mettre de la TVA sur un paiement. Avant de répondre, on a vérifié l'historique Git : aucun interrupteur n'avait été retiré, le champ du taux acceptait 0 depuis le début. Le défaut n'était donc pas une règle, mais un manque d'explication : rien ne disait qu'il fallait taper 0, et un coach sans TVA voyait quand même « TVAC » et « 0 % ». La correction suit ce que les dépenses faisaient déjà : sans TVA, l'interface n'en parle pas ; avec TVA, une case « Appliquer la TVA », cochée par défaut, rend l'exception visible. Côté données, rien ne change (un taux de 0) : c'est une correction d'interface, pas de base de données. Leçon : quand un utilisateur croit qu'une chose est obligatoire, c'est souvent l'écran qui le lui fait croire.

### Un même geste partout sur le téléphone (04/11)
Après les boîtes, Antonino a remarqué deux incohérences sur téléphone : le bouton « + » était tantôt en haut à droite, tantôt flottant en bas (Agenda), et certaines pages montraient leur nom dans la barre du haut, puis un « ← Retour » dessous, puis encore leur titre. On a choisi une règle par élément plutôt qu'une retouche par page : le « + » est toujours le bouton flottant de l'Agenda (une seule classe partagée, `phoneFabClass`), et le retour se pose toujours dans la barre du haut (l'en-tête commun s'en charge pour toutes les pages qui ont un retour). Le libellé du retour suivait déjà la page d'où l'on vient depuis le 29/10 (l'app retient la page précédente de l'onglet), il suffisait de le déplacer. Un piège rencontré : pour laisser de la place sous le bouton flottant, la première règle CSS disait « si la page contient un bouton flottant » ; or Next garde la page qu'on vient de quitter cachée dans le document, avec son bouton, et la règle se déclenchait sur la page suivante. On l'a limitée au `<main>` de la page affichée.

### Un test qui échoue seulement quand tout tourne (04/11)
Après le nouveau menu du compte, un test (l'invitation d'un sportif) s'est mis à échouer, mais seulement dans la suite complète : seul, il passait 12 fois sur 12. Sa trace montrait la scène : déconnexion, arrivée sur la page de connexion, saisie de l'e-mail et du mot de passe, puis envoi… avec des champs vides. Plutôt que de conclure à un hasard, on l'a fait tourner exprès sous charge, à côté d'autres tests lourds : 2 échecs sur 3, le problème était reproductible. La cause : le menu du compte est maintenant une vraie fenêtre modale, et il restait ouvert pendant que l'app partait vers la page de connexion ; pendant cet instant, la nouvelle page n'acceptait pas encore la saisie. Le menu se ferme désormais au moment où l'on clique sur « Se déconnecter », comme on s'y attend de toute façon : 3 sur 3 sous la même charge. Leçon : un test « instable » est souvent un vrai défaut de timing, qu'on peut reproduire en recréant les conditions où il échoue.

### Les PDF des programmes (10/11)
Un coach imprime ou envoie le programme : deux PDF, « Agenda du programme » (une page par semaine) et « Fiches et repères » (le détail de la musculation et des circuits Hyrox, les allures). Ils sont fabriqués à la demande, toujours depuis la version publiée, jamais depuis le brouillon : le sportif, le PDF et l'app montrent la même chose. Le moteur était déjà choisi (React-PDF, ADR 0002) : on écrit le document en composants React, le serveur produit un vrai PDF, sans navigateur à faire tourner. Pour garder le code lisible, le contenu de chaque page (quelle semaine, quels liens ‹ ›, quelles lignes) est calculé par des fonctions pures et testées ; le document ne fait que dessiner. Les liens du sommaire et des boutons ‹ › sont de vrais liens internes du PDF, et chaque page a son signet. La police de l'app est intégrée au fichier, sinon un lecteur afficherait une autre police.

*Ce qu'on a appris :* un PDF n'a pas de défilement, chaque page a une hauteur fixe. Il faut donc prévoir ce qui tient sur une page (une semaine chargée se raccourcit, une fiche longue continue « (suite) »), et le vérifier : un test rend les deux PDF pour de vrai et compare le nombre de pages au plan prévu.

### Un deux-points qui se pose tout seul (10/11)
Sur iPhone, le pavé numérique n'a pas de « : », et une page web ne peut ni ajouter une touche ni changer de clavier. Plutôt que d'ouvrir le clavier complet (lent au pouce), le champ d'allure pose le « : » pendant la frappe : on tape 455, il affiche 4:55. Une durée, elle, peut s'écrire en minutes seules (45) : là, le « : » automatique fausserait la saisie, donc on ouvre le pavé décimal et sa virgule sert de séparateur (2,30). Même jour, le détail d'une séance dans l'éditeur a pris les règles des cartes de l'agenda grâce à un composant de ligne commun : une seule façon d'écrire une ligne de séance dans toute l'app.

### « Ça ne se synchronise pas » : brouillon et version publiée (10/11)
Antonino a modifié une séance depuis la fiche d'une sportive, puis ne voyait pas le changement dans ses onglets. Ce n'était pas un bug : le changement était bien enregistré, mais dans le brouillon, alors que la sportive (et ses onglets, et les PDF) suit la version publiée. C'est une règle de base du projet : on ne montre jamais au sportif un programme à moitié modifié. Plutôt que de casser la règle, on l'a rendue visible et rapide : un bandeau dit « Anaïs voit encore la version 1 » et publie la version 2 en un geste, avec les mêmes vérifications que l'éditeur, réunies dans un seul module. Leçon : avant de « corriger », vérifier dans la base où sont les données ; ici, une question de produit, pas un défaut de code.

### Phase 4 : tout reprendre, ligne par ligne (10/11)
Les maquettes « Programmes » venaient avec une liste de 80 contrôles (chaque bouton, ce qu'il doit faire) et 18 cas de test. Les écrans étaient faits ; il restait à prouver que chaque contrôle marche. Plutôt que de survoler, trois vérifications ont relu le code en parallèle, une par groupe d'écrans, puis chaque manque a été recontrôlé avant d'écrire une ligne. Résultat honnête : une soixantaine de contrôles faits, une vingtaine à moitié, quelques vrais défauts (une modification pouvait se perdre si l'enregistrement échouait au moment de quitter ; la façon de viser choisie dans l'assistant n'était jamais reprise). Quatre points étaient des choix de produit, posés à Antonino plutôt que tranchés à sa place. Chaque cas de test porte maintenant son numéro dans le nom du test, ce qui permet de dire exactement ce qui est couvert, et ce qui ne l'est pas encore (le sportif qui déplace une séance attend son espace).

*Ce qu'on a appris :* écrire le test d'abord et le voir échouer prouve qu'il teste la bonne chose. Et un test peut être faux lui-même : celui des modèles comptait tous les modèles de la base, il ne passait que sur une base vide.

### Recette : comparer, mesurer, et dire ce que le chiffre veut dire (11/11)
Dernière phase des maquettes « Programmes » : capturer les 41 écrans de l'app dans l'état le plus proche de leur maquette, les mettre côte à côte, mesurer la part de pixels différents, puis corriger. Le chiffre (2 à 38 %) ne mesure pas la qualité : les données, la date et les couleurs de l'app diffèrent exprès des maquettes. On l'a donc écrit tel quel, en disant pourquoi, et jugé chaque écran à l'œil. La recette a trouvé de vrais défauts que personne n'avait vus : deux chevrons superposés dans toutes les listes déroulantes (un composant et une règle globale dessinaient chacun le leur), des boutons qui s'écrasaient à 22 px dans la fenêtre « Publier » sur téléphone, un tableau de bord qui pouvait cacher tous les programmes en cours. Le même jour, Antonino a signalé un menu coupé par une liste qui défile : la solution propre a été de l'ouvrir dans la « couche supérieure » du navigateur (API Popover), où aucun conteneur ne peut plus le couper.

*Ce qu'on a appris :* une maquette donne une cible, pas une vérité : Antonino a trouvé trop tassée une colonne pourtant fidèle au pixel près. On l'a aérée, et c'est sa lecture d'utilisateur qui compte.

### TVA : la règle était bonne, les données non (11/11)
Antonino voulait une TVA à 0 % par défaut, et que l'app calcule à 21 % dès qu'on règle 21 % dans les Paramètres. En lisant le code, la règle existait déjà : chaque montant se calcule depuis le taux de l'organisation. Ce qui ne collait pas, c'étaient les données de démonstration, restées à 21 % alors que les organisations étaient à 0 %. On a corrigé la graine, aligné la base de développement sans l'effacer (avec une copie de sauvegarde avant), et changé les tests : chaque test qui vérifie la TVA règle lui-même le taux à 21 %, et une étape de fin de suite remet 0 %.

*Ce qu'on a appris :* quand « l'app n'est pas logique », il faut d'abord séparer la règle (le code) de ce qu'elle reçoit (les données). Et un test ne doit jamais compter sur un réglage laissé par quelqu'un d'autre : il prépare ce dont il a besoin.

### La TVA là où se trouve l'argent (11/11, soir)
Quelques heures après avoir mis la TVA « de base à 0 % » dans les Paramètres, Antonino a proposé plus simple : une case « Appliquer la TVA » dans chaque paiement, chaque dépense et chaque séance, et plus de réglage global. C'est plus juste pour Gianluca, qui travaille à la fois en indépendant (avec TVA) et pour une ASBL (sans). La base gardait déjà un taux par paiement et par dépense ; la séance a reçu le sien (une petite migration), et le paiement noté en la marquant payée le reprend. La Comptabilité, elle, calculait déjà ligne par ligne : il a suffi de ne plus dépendre d'un réglage.

Le même soir : l'assistant « Nouveau programme » a sa page dans la fiche du sportif (on ne le recherche plus dans une liste), et « Ajouter une séance » propose toutes les disciplines, pour qu'un programme running accueille un renfo jambes.

*Ce qu'on a appris :* un réglage global est une règle cachée ; mettre la décision là où l'utilisateur agit rend l'app plus lisible. Et un bon modèle de données (un taux par ligne) rend ce genre de changement court.

### Deux, trois, quatre séances le même jour (11/11, soir)
Gianluca fait parfois s'entraîner ses sportifs deux fois par jour. Avant de coder, on a montré à Antonino une proposition visuelle (une page de démonstration et des captures) ; il a choisi : jusqu'à 4 séances par jour, 14 par semaine, et un moment pour chaque séance d'un jour chargé (matin, midi, après-midi, soir). Le modèle de données le permettait presque déjà : il a suffi d'un champ « moment » dans la séance, d'une règle de tri (le jour, puis le moment) et de quelques garde-fous (un jour à 4 séances est complet). Le reste est de l'affichage, partout où une séance apparaît.

*Ce qu'on a appris :* montrer une maquette avant de coder fait gagner du temps : Antonino a corrigé la limite (4 et non 2) avant qu'elle soit écrite dans le code.

### Des plans de course prêts à l'emploi (11/11, soir)
Coory propose maintenant trois modèles de course : 10 km, semi-marathon et marathon, chacun avec une séance de renforcement des jambes et des chevilles par semaine. Les plans ont été écrits par un script, puis vérifiés par les mêmes règles que l'app (schémas Zod) et contre la vraie Bibliothèque (chaque exercice existe). Écrire ces plans a aussi révélé deux limites de l'app, notées pour plus tard.

*Ce qu'on a appris :* du contenu « métier » se teste comme du code : un plan qui ne passe pas le schéma ne doit jamais arriver jusqu'au coach.

### Une planche se compte en secondes (13/11)
Écrire les plans de course avait montré une limite : une série ne pouvait se compter qu'en répétitions, alors qu'une planche ou un équilibre se tiennent un temps. Une série a maintenant deux façons d'être comptée, et l'éditeur a un choix « Mesure ». La Bibliothèque savait déjà quels exercices se mesurent en secondes (une information du catalogue) : l'éditeur s'en sert pour proposer « 3 × 30 s » d'office.

*Ce qu'on a appris :* rendre un champ facultatif touche tous les endroits qui le lisent ; un seul formateur partagé (« 8–10 » ou « 30 s ») évite d'avoir cinq façons d'écrire la même chose.

### Un MVP qui ne promet que ce qu'il tient (13/11)
Pour la mise en ligne, Coory devient un « espace coach seul » : la messagerie, les invitations et l'espace sportif sont masqués, parce que l'autre côté (le sportif connecté) n'existe pas encore. Plutôt que d'effacer du code, trois drapeaux dans un seul fichier coupent ces fonctions à tous les étages : l'adresse (le proxy redirige), la page (elle répond « introuvable ») et l'action serveur (elle refuse, même appelée directement). Les boutons « Écrire » et « Inviter » restent, mais disent honnêtement « pas encore disponible ».

*Ce qu'on a appris :* masquer une fonction, c'est comme la sécuriser : il faut fermer chaque porte, pas seulement retirer le bouton.

### L'IA payante, protégée par la base (13/11)
L'Assistant IA appelle Claude, et chaque demande coûte. Règle d'Antonino : aucun appel sans abonnement. Le contrôle est dans PostgreSQL, pas seulement dans l'interface : une fonction réserve la demande AVANT l'appel (abonnement de l'organisation, 100 demandes par mois), sous un verrou pour que deux onglets ne dépassent pas la limite ensemble. Le coach ne peut pas s'abonner lui-même : la colonne n'accepte aucune modification de sa part. La clé de l'API reste sur le serveur, et un plafond de dépense dans la console Anthropic sert de dernier filet.

*Ce qu'on a appris :* pour une ressource qui coûte de l'argent, la limite doit vivre au même endroit que les données, pas dans le navigateur.

### Une revue avant d'ouvrir la porte (13/11)
Avant la mise en ligne, une revue complète a passé en revue la création de programmes, la fiche du sportif et la sécurité ; tout a été corrigé dans la foulée. Exemples : une séance riche (31 étapes de course) disparaissait parce qu'elle était revérifiée avec les limites d'un ancien format ; une session restée ouverte suffisait pour changer de mot de passe sans l'ancien (il faut maintenant le lien reçu par e-mail, reconnu à la « méthode de connexion » inscrite dans le jeton) ; les documents de 10 Mo auraient échoué chez l'hébergeur, limité à 4,5 Mo. Le guide `docs/DEPLOIEMENT.md` décrit la mise en ligne étape par étape.

*Ce qu'on a appris :* les bugs les plus coûteux sont à la frontière entre deux versions d'un même format, ou entre le code et la plateforme qui l'héberge.

### Un assistant qui prépare, un coach qui valide (13/11)
L'Assistant IA peut maintenant agir dans Coory : créer une séance, noter un paiement, ajouter une tâche… Claude reçoit des « outils ». Ceux qui lisent (retrouver un sportif, regarder l'agenda) s'exécutent tout de suite ; ceux qui écrivent ne s'exécutent jamais : ils produisent une carte que le coach valide d'un clic. Ce clic passe par exactement le même code que le formulaire habituel, donc les mêmes règles et les mêmes droits. Pour les tests, un « faux Claude » rejoue des réponses écrites à l'avance : on vérifie tout le parcours sans payer un seul appel.

*Ce qu'on a appris :* avec une IA qui agit, la sécurité ne vient pas de ce qu'on lui demande dans la consigne, mais de ce qu'on la laisse faire : ici, proposer seulement, jamais exécuter.

### Parler à l'assistant plutôt qu'écrire (13/11)
Gianluca peut maintenant dicter sa demande : un bouton micro dans la saisie de l'assistant. La reconnaissance vocale n'est pas codée dans Coory, c'est celle du navigateur (Chrome ou Safari), gratuite. Coory ne reçoit que le texte, qui s'écrit en direct dans la saisie : le coach le relit et l'envoie lui-même. Le micro n'est autorisé que pour Coory (en-tête `Permissions-Policy`), et le bouton n'apparaît pas là où il ne marcherait pas (Firefox, adresse non sécurisée).

*Ce qu'on a appris :* tester une fonction du navigateur sans le navigateur réel, c'est le remplacer par un faux qui a la même interface. Et ce faux doit remplacer *tous* les noms possibles : Chromium fournit aussi la version sans préfixe, que le code choisit en premier.

### Un programme écrit par l'IA, mais jamais publié par elle (13/11)
L'assistant sait maintenant préparer un programme complet. Il part de préférence d'un modèle existant (plus sûr, moins long), sinon il écrit les séances. Pour que sa réponse reste courte, il décrit chaque séance une seule fois avec une petite référence (« A », « footing »), puis la place semaine par semaine : le serveur reconstruit le programme. On ne fait pas confiance au texte de l'IA : le programme passe par les mêmes schémas que l'éditeur, les exercices doivent exister dans la Bibliothèque du coach, et le résultat reste un brouillon que le coach publie lui-même.

*Ce qu'on a appris :* réutiliser les schémas de validation existants, c'est ce qui rend une IA fiable sans réécrire de règles : une seule définition de « séance valide », pour le coach comme pour l'assistant.

## 8. Problèmes rencontrés et ce qu'ils ont appris

Ces incidents sont de bons sujets d'entretien : ils montrent qu'on teste vraiment.

- **« Date.now() pendant le prérendu »** : Next 16 essayait de pré-calculer la page coach, alors que la session dépend de l'heure. Solution : `connection()` force le calcul à chaque requête. Bonus : les données personnelles ne sont jamais en cache.
- **L'adresse restait sur `/espace` après connexion** : la page affichée était bonne, mais l'URL non. Trouvé par Playwright, corrigé en redirigeant directement au bon endroit.
- **L'inscription libre était ouverte** : sans page d'inscription, l'API de Supabase acceptait quand même de créer des comptes. Fermé dans la configuration et vérifié.
- **Des tests « chanceux »** : deux fois, un test cliquait puis naviguait sans attendre la fin de l'action (déconnexion, changement de page). Il passait par chance de timing, puis a échoué plus tard. Leçon : toujours attendre un signe visible (nouvelle adresse, nouveau titre) avant l'étape suivante, et relancer la suite plusieurs fois pour vérifier sa stabilité.
- **« styleText n'existe pas »** : Vitest refusait de démarrer. Le terminal utilisait une ancienne version de Node, pas la version 24 du projet. Leçon : quand un outil plante dès le démarrage sur une fonction de Node, vérifier d'abord `node -v`.
- **« Il n'y a pas de couleurs »** : après le graphite, Antonino trouvait encore la fiche terne. Nouvelle série d'aperçus, nouveau choix : un sombre encore plus clair, et des couleurs qui gardent un sens (l'en-tête prend la couleur de la discipline de l'objectif principal, chaque chiffre clé a sa pastille). La mesure a refusé une seule idée : des initiales orange sur un avatar orangé n'étaient pas assez lisibles, elles restent donc en couleur texte. Leçon : un design system est un point de départ ; quand l'utilisateur final le trouve terne, on l'adapte, mais en documentant l'écart et en vérifiant la lisibilité.
- **« Le dark est trop dark »** : plutôt que de discuter de couleurs dans le vide, on a produit quatre aperçus de la même fiche (actuel, graphite, bleu nuit, icônes colorées) en injectant les couleurs seulement dans le navigateur qui prend la capture, sans toucher au code. Antonino a choisi sur image. Retenu : un fond graphite, et des couleurs qui ont un **sens** (une par discipline) plutôt que décoratives. Effet de bord évité : le rouge texte a dû s'éclaircir pour rester lisible sur le graphite, alors le logo a reçu son propre jeton pour garder le rouge exact de la marque.
- **« On ne lit pas très bien en sombre »** : Antonino avait raison, et les chiffres l'ont confirmé. Le texte « discret » n'atteignait que 2,5:1 de contraste, alors que la norme d'accessibilité (WCAG) demande 4,5:1. Plutôt que d'éclaircir au jugé, on a mesuré chaque couple texte / fond avec la formule officielle, avant et après. Grâce aux jetons, la correction a tenu en cinq valeurs dans un seul fichier. On a même évité un effet de bord : le rouge du logo utilise le même jeton que le texte rouge, on l'a donc laissé intact et corrigé le fond de la pastille à la place.
- **Une liste déroulante qui oubliait la saisie** : après une erreur, React remettait les listes déroulantes et les cases à cocher à leur valeur de départ (les champs texte, eux, étaient bien conservés). Trouvé par un test, corrigé dans les deux formulaires concernés. Leçon : tester la conservation de la saisie pour chaque **sorte** de champ, pas seulement pour les champs texte.
- **« Ça marche chez moi, pas dans les tests »** : avec Next 16, la page qu'on vient de quitter reste dans la page, **cachée**, pour un retour instantané. Un test qui cherchait « le » champ Sportif en trouvait deux : le vrai, et la carte Sportif de la page précédente, invisible. Leçon : chercher les éléments par leur **rôle** (liste déroulante, bouton), qui ignore ce qui est caché.
- **Une heure de 0 pixel** : la hauteur d'une heure dépendait d'une variable CSS (`--span`) posée sur un élément enfant. Or une variable se calcule là où on la déclare : sur le parent, elle n'existait pas, et toute la grille s'écrasait. Trouvé en mesurant au navigateur, pas en relisant le code.
- **Une sauvegarde qui écrasait la bonne copie** : le script qui garde la session pendant les remises à zéro ne restaurait rien si le reset échouait (étapes enchaînées par `&&`), puis la sauvegarde suivante enregistrait l'état vide par-dessus. Leçon : une étape de restauration doit tourner quoi qu'il arrive, et une sauvegarde ne doit jamais remplacer une meilleure copie.
- **Une icône qui se faisait passer pour un champ** : l'icône « Fiche à compléter : nom de famille, e-mail ou téléphone » portait ce texte en `aria-label`. Les tests qui cherchaient le champ « Téléphone » par son libellé la trouvaient aussi (24 tests en échec d'un coup). L'icône annonce maintenant juste « Fiche à compléter », le détail est dans l'infobulle, et les tests cherchent les champs par leur rôle.
- **Deux tests qui se marchaient dessus** : en parallèle, deux tests créaient une séance au même créneau ; la séance de l'un recouvrait le créneau de l'autre. Leçon : chaque test garde sa semaine et son heure, comme s'il était seul.
- **Un droit trop large refusé à juste titre** : « créer ou mettre à jour » (upsert) une date déplacée échouait, car il réécrit aussi des colonnes que le navigateur n'a pas le droit de modifier. La base avait raison : on lit d'abord, puis on met à jour ou on crée.
- **« SECTIONS.find is not a function »** : une liste exportée d'un fichier `"use client"` et lue par une page serveur n'est pas la liste, mais une référence vers le code du navigateur. Leçon : un fichier client n'exporte que des composants ; les données partagées vont dans un module neutre.
- **« Ce site est inaccessible », seulement sur le vrai iPhone** : l'app s'ouvrait sur le téléphone, puis plus rien une fois connecté. La page `/espace` renvoyait le navigateur vers `http://0.0.0.0:3000/coach` : l'adresse avait été reconstruite à partir de `request.url`, qui contient l'adresse d'écoute du serveur, pas celle tapée par le téléphone. Sur le Mac, `0.0.0.0` désigne la machine elle-même, donc tout marchait en local et dans les tests. La correction est d'utiliser des redirections **relatives** (`redirect("/coach")`), que le navigateur complète avec sa propre adresse. Leçon : tester sur un vrai appareil révèle des bugs que l'ordinateur de développement masque, et le journal du serveur (`.next/dev/logs`) a donné l'indice décisif.
- **Une correction qui a tout cassé** : en fermant l'inscription, un deuxième réglage a coupé toute connexion. Les tests l'ont attrapé immédiatement. Leçon : c'est exactement pour ça qu'on a des tests automatiques.

- **Un PDF aux pages trop courtes, puis trop longues** : avec React-PDF, interdire à une page de déborder (`wrap={false}`) lui donne la hauteur de son contenu au lieu du format A4 ; et une hauteur estimée trop courte pousse le pied de page sur une page vide. Trouvé en convertissant chaque page en image et en mesurant la position des lignes. Leçon : vérifier un document imprimable par des mesures, et un test qui compare le nombre de pages rendues au nombre prévu.
- **Deux chevrons dans chaque liste** : un composant dessinait son chevron, et une règle CSS globale (hors couche, donc prioritaire) en ajoutait un autre en image de fond. Invisible tant qu'ils se superposaient presque, flagrant quand les tailles différaient. Corrigé en excluant de la règle les listes qui dessinent le leur. Leçon : une règle globale « hors couche » gagne contre tout utilitaire, il faut lui prévoir une sortie.
- **Un menu coupé par une liste qui défile** : un menu en `position: absolute` ne peut pas sortir d'un parent `overflow: auto`. L'API Popover du navigateur le place dans la couche supérieure, au-dessus de tout, sans calcul de `z-index`.
- **Un test qui dépendait des données de démonstration** : le test SQL des modèles attendait « 1 modèle Coory », mais la base de développement en contient déjà deux pour les démonstrations. Il ne passait que sur une base vide. Il ne lit plus que ses propres lignes. Leçon : un test doit fabriquer et regarder ses propres données, jamais compter ce qui traîne dans la base.
- **Des lignes de sommaire géantes** : six lignes de 52 px rendues à 121 px. Cause isolée par essais successifs (3 lignes : bien ; 6 lignes identiques : mal) : un défaut de React-PDF avec `minHeight`. Remplacé par un rembourrage équivalent. Leçon : réduire un bug à son plus petit cas avant de corriger.

## 9. Questions probables d'un recruteur

- **« Comment garantis-tu qu'un coach ne voit pas les clients d'un autre ? »** Trois couches (proxy, garde-fous serveur, RLS), et 133 tests SQL, 74 tests unitaires et 55 tests navigateur qui le prouvent avec deux organisations.
- **« Pourquoi pas un backend séparé ? »** Next.js exécute déjà du code serveur. Un second backend doublerait le travail et les risques, sans bénéfice à cette échelle.
- **« Comment tu testes ? »** Trois niveaux : pgTAP pour la base, vérifications HTTP, Playwright pour les parcours sur ordinateur et téléphone.
- **« Comment gères-tu des données de santé ? »** Le moins possible : un champ court, sans diagnostic, qui n'existe que pendant un accord explicite du sportif. La base le garantit (contrainte + fonctions qui vérifient l'appelant), chaque accord est journalisé, et le retrait efface les données. Le sportif voit ce qui est noté sur lui.
- **« Comment gères-tu le thème sombre et clair ? »** Toutes les couleurs sont des variables CSS. Un attribut sur `<html>` change leur valeur, donc aucun composant n'a besoin de savoir quel thème est actif. Un script lancé avant l'affichage évite le flash.
- **« Comment as-tu utilisé l'IA ? »** Claude Code écrit le code à partir d'un cahier des charges détaillé ; je valide chaque décision métier, je teste dans le navigateur, et tout est tracé dans un journal avec les preuves de tests.

## 10. Petit glossaire

- **Tenant / organisation** : l'espace isolé d'un coach ou d'un studio.
- **RLS** : règles dans PostgreSQL qui filtrent les lignes selon l'utilisateur connecté.
- **Migration** : fichier SQL daté qui fait évoluer le schéma de la base.
- **Seed** : données de démonstration chargées après les migrations.
- **Server Action** : fonction serveur appelée directement par un formulaire.
- **Proxy** : code exécuté avant chaque requête (s'appelait « middleware » avant Next 16).
- **PKCE** : mécanisme qui garantit qu'un lien reçu par e-mail ne fonctionne que dans le navigateur qui l'a demandé.
- **E2E (end-to-end)** : test d'un parcours complet, du clic à la base de données.
- **IDOR** : attaque qui consiste à changer un identifiant dans l'adresse pour accéder aux données de quelqu'un d'autre.
- **Segment dynamique** : partie variable d'une adresse, comme `[orgId]`.
- **Domaine (code de)** : les règles métier pures (calculs, validations), indépendantes de la base et de l'interface.
- **Hash (empreinte)** : transformation à sens unique d'un texte. On peut vérifier qu'un lien correspond à l'empreinte, mais pas retrouver le lien à partir d'elle.
- **VMA** : vitesse maximale aérobie, la vitesse de course à partir de laquelle on calcule les allures d'entraînement.
- **Atomique** : une opération qui réussit entièrement ou ne change rien du tout.
- **ADR** : courte note qui documente une décision technique, ses alternatives et ses conséquences.
- **Colonne calculée** : colonne dont la base calcule elle-même la valeur à partir d'autres colonnes (ici le nom complet) ; on ne peut pas l'écrire.
- **Données de santé (RGPD art. 9)** : catégorie de données sensibles ; on ne peut les traiter qu'avec un accord explicite (ou une autre base légale précise).
- **Fonction SECURITY DEFINER** : fonction de la base qui s'exécute avec des droits élevés ; elle doit donc vérifier elle-même qui l'appelle avant d'agir.
- **Piste d'audit (journal)** : liste d'événements datés qu'on ne peut que compléter, jamais modifier, pour prouver ce qui s'est passé.
- **Contraste (ratio WCAG)** : rapport de luminosité entre un texte et son fond, de 1:1 (invisible) à 21:1 (noir sur blanc) ; 4,5:1 minimum pour un texte normal.
- **Index unique partiel** : règle de la base qui interdit les doublons seulement pour certaines lignes (ici : un seul objectif principal parmi ceux en cours).
- **Liste fermée** : ensemble de valeurs autorisées (ex. Débutant, Intermédiaire, Confirmé, Compétiteur), vérifié par le serveur et par la base.
- **Token (design)** : une valeur de design nommée (couleur, rayon, taille) définie une fois et réutilisée partout.
- **Thème / data-theme** : attribut posé sur `<html>` qui fait basculer toutes les variables de couleur d'un coup.
- **Flash (FOUC)** : bref affichage dans le mauvais style avant que le bon s'applique ; évité ici par un script dans `<head>`.
- **SVG** : dessin vectoriel écrit en code (des tracés plutôt que des pixels), net à toutes les tailles ; c'est le format du logo.
- **Contraste** : rapport de luminosité entre un texte et son fond ; la norme d'accessibilité demande 4,5 pour 1 pour un texte normal.
- **TVAC / HTVA** : toutes taxes (TVA) comprises / hors TVA. Le chiffre d'affaires d'un assujetti à la TVA se compte HTVA.
- **Comptabilité de caisse** : on compte un revenu le jour où l'argent est reçu, pas le jour où le service est rendu.
- **Mise à jour optimiste** : l'écran montre tout de suite le résultat d'un clic, avant la réponse du serveur, et revient en arrière si elle échoue.
- **Exception (de récurrence)** : une date d'une série hebdomadaire qui a lieu ailleurs (autre jour ou autre heure), notée à part sans toucher à la série.
- **Déclencheur (trigger)** : petit programme de la base lancé automatiquement à chaque écriture, pour vérifier ou compléter une ligne.
- **Devise ISO 4217** : code à trois lettres d'une monnaie (EUR, CHF, USD) ; Coory ne garde que celles qui ont des centimes.
- **SECURITY INVOKER** : fonction de la base qui s'exécute avec les droits de celui qui l'appelle (le contraire de SECURITY DEFINER).
- **Clé secrète (service role)** : clé Supabase qui contourne la RLS ; réservée au serveur, à quelques procédures précises.
